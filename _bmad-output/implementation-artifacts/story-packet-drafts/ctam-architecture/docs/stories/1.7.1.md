# Story 1.7.1: Both groups of users can be seeded, verified against the sign-in system, and set up for real via a runbook

Status: ready-for-dev

## Story

As the **person responsible for identity setup, and every engineer who needs working sign-in in every environment**,
I want seed scripts covering both groups of users, a repeatable check that proves every user maps to a real sign-in identity, and a written runbook for setting this up for real,
So that **sign-in works end-to-end everywhere it's needed, and nobody can go live for a group of users whose identities haven't been proven to actually work**.

## Acceptance Criteria

1. **Given** the engineer writes the development/test seed scripts (a one-off setup script, not something that runs as part of the live system, and not part of the ordinary database change process), **when** the scripts run against a freshly created development or test database, **then** they create: realistic sample judicial-holder records — including personnel records whose email addresses match the judicial test users already used for sign-in testing, with stable personnel numbers, a freshly-generated CTAM reference for each one, and sample jurisdictions covering Employment Tribunals, the Social Security and Child Support tribunal, and example ordinary courts; **and** administrative-staff identity records whose email addresses match the administrative test users already used for sign-in testing; **and** combined user records for both groups — each tagged as judicial or administrative, linked to the correct underlying identity record, and recording which jurisdiction they belong to; **and** role assignments and Region/Area coverage records covering every documented role in both groups; **and** activation-status records for every jurisdiction/region combination — all switched **off** by default, except a handful of designated test users deliberately switched **on**, so the sign-in demo can show both the "activated" and "not yet activated" experience; **and** the scripts can be safely re-run against a database that's already been seeded, without creating duplicates or breaking anything.

2. **Given** the verification check is built (a repeatable script or scheduled job, owned by the architecture team), **when** it runs against an environment, **then** for every user record, in both groups, it confirms the person actually exists in the sign-in system — checked by email against a stand-in sign-in directory during earlier phases, and against the real HMCTS sign-in directory once the programme cuts over to it; **and** it checks that the underlying data is internally consistent for each group: every judicial user record links to a valid judicial-holder identity whose personnel number maps to an active personnel record; every administrative-staff user record links to a valid staff-identity record; **and** it produces a report showing, per group, the total number of users, how many were successfully verified, and the specific reason for any that weren't; **and** if even one user fails to verify, the check fails outright — and passing this check cleanly is a required step before any jurisdiction/region combination can go live; **and** running the check never changes any data — it only checks and reports.

3. **Given** the written runbook for setting this up for real, **when** programme management prepares the users for a jurisdiction going live, **then** the runbook spells out exactly what programme management must supply — the list of administrative staff identities with their email addresses, and the role/jurisdiction/area-coverage assignments for both groups (judicial-holder personal data itself arrives separately, through the ongoing sync with the judicial data source, not through this setup process); **and** it documents, table by table, how a database administrator loads that data — including the rule that everyone starts switched off by default; **and** it explains how to run the verification check, and states plainly that a clean pass is required before that jurisdiction/region combination can go live; **and** it explains how a database administrator makes an ongoing change to someone's role, jurisdiction, or coverage area, including how that change gets recorded for audit purposes; **and** it states plainly what this process does **not** do: there is no import of user accounts from any legacy system, and the underlying source of the real user list is programme management's responsibility, not something this process provides.

4. **Given** the seed scripts have run in a development environment, **when** the automated sign-in test suite runs, **then** the judicial test user can sign in and resolves correctly to their CTAM reference, and the administrative-staff test user can sign in and resolves correctly to their staff identity; **and** the verification check passes cleanly against that seeded environment as part of the automated build.

## Dev Notes

### Context distilled from the bus

- **FR1** — identity resolution shape both the seed data and the verification check must produce: IdP email → `jo_people` → `personnel_number` → `ctam_joh_identities` UUID for a JOH; IdP email → `ctam_auth_staff_identities` UUID for admin staff. [Source: _arch/architecture/fr-coverage-map... — cited via the canonical FR/epic mapping] and [Source: _arch/architecture/data-tables.md#authorisation-service-ctam-authorisation-6-tables — `ctam_auth_users` row]
- **FR4** — this story is explicitly the "data layer only" half of FR4: the auth tables are maintainable by DBAs via direct SQL per the identity-bootstrap runbook this story produces. The sysadmin UI surface over the same data is post-MVP and out of scope here. [Source: _arch/architecture/data-tables.md#authorisation-service-ctam-authorisation-6-tables]
- **FR57** — this story only delivers the *initial all-FALSE flag state* keyed by `(jurisdiction, region)` in `ctam_auth_user_activation_flags`. The wave-cutover flip itself (`UPDATE ctam_auth_user_activation_flags SET activated = TRUE WHERE jurisdiction = '…' AND region = '…'`) is a later, Phase 9+ concern, run per the rollout runbook — not built by this story, only set up so that runbook has something correct to flip. [Source: _arch/architecture/data-tables.md#authorisation-service-ctam-authorisation-6-tables — `ctam_auth_user_activation_flags` row]
- The six auth tables this story seeds and verifies against (`ctam_auth_users`, `ctam_auth_staff_identities`, `ctam_auth_roles`, `ctam_auth_user_roles`, `ctam_auth_user_region_scopes`, `ctam_auth_user_activation_flags`) are **strictly CTAM-internal**: no external authority provides this data and no legacy system seeds it — matches the epic's "no legacy carry-over" framing exactly. [Source: _arch/architecture/data-tables.md#authorisation-service-ctam-authorisation-6-tables]
- The JOH side resolves through `ctam_joh_identities` (`id uuid PK` + unique `personnel_number` link to `jo_people`, audit columns), minted eagerly by the nightly eLinks sync — this story's JOH seed rows must look like eagerly-minted rows, not synthesize a different shape. [Source: _arch/architecture/data-tables.md#ctam-owned-joh-identity-1-table]
- S12 (mock auth never reaches production) governs the verification check's target: during earlier phases it checks against `ctam-mock-auth`'s roster; the runbook must describe the cutover to the real HMCTS directory as a configuration change, never a fallback. [Source: _arch/agent-rules/50-security-and-logging.md#s12-mock-auth-never-reaches-production]

### Project Structure Notes

- **Unusual case, called out explicitly:** this story's target repo (`ctam-architecture`) and the context bus it would normally consume as a pinned submodule are **the same repo**. There is no separate `_arch/` checkout to pin against — the rules and data-table definitions cited above are read directly from this repo's own `architecture/` and `agent-rules/` trees, at whatever commit this story lands on. `bus_version: arch-v1.1` records the tag this packet was drafted against, not a submodule pin.
- `ctam-architecture`'s documented directory tree names a `runbooks/` folder (currently holding `incident-response.md` and `per-region-rollout-playbook.md`) — the new runbook belongs there, e.g. `runbooks/identity-bootstrap-runbook.md`, following that existing naming pattern. [Source: _arch/architecture/repo-structure.md — `ctam-architecture/` tree, `runbooks/` entry]
- The one directory in the documented tree that looks superficially similar — `migration/` (extract/reconcile/load scripts against APEX, including a `users-roles/` subfolder) — is explicitly marked as **not existing**, retired per the revised no-legacy-migration decision. This story's seed scripts and verification job are a different thing (dev/test bootstrap + a standing verification job, not a one-off legacy migration) and must not be built into that retired tree or modelled on its "write only via API" rule. [Source: _arch/architecture/repo-structure.md — `(migration/ — does not exist...)` note and its rationale]
- **Open point (R5 — flag, do not guess):** no cited convention states whether the dev/test seed scripts and the verification job write/read the six `ctam_auth_*` tables directly via SQL, or by calling `ctam-authorisation`'s own APIs once they exist. `ctam-authorisation` owns those tables (Story 1.4.3); the retired `migration/` pattern's "always via API" rule doesn't carry over automatically since it no longer applies. Resolve this with the architecture team before writing Task 1/Task 2's production code, and record the answer here once known.
- No Spring Boot service-layer structure applies here (`ctam-architecture` is not a runtime service) — these are standalone scripts/a job plus a markdown runbook, not a `controller/`/`service/`/`repository/` package tree.

### Out of scope / boundaries

- Any on-screen tool for administrators to manage users, roles, jurisdiction, scope, or activation status.
- Where programme management actually gets its real, live list of users from — that's outside this work.
- Any process for importing or reconciling user accounts from a legacy system — none exists or is planned.
- Actually supplying the real, live list of users for a production go-live — this story only provides the runbook and the verification check, not the source data itself.
- The wave-cutover flip itself (`UPDATE ctam_auth_user_activation_flags SET activated = TRUE …` per jurisdiction/region) — that's the Phase 9+ rollout runbook's job; this story only sets up the correct initial all-FALSE state (FR57) for it to act on later.
