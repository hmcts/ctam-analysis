## Story

As a **calling service or the front-end application**,
I want every CTAM Pathfinder request to pass through a token-checking filter and have the person's confirmed identity, roles, jurisdiction, and region/area scope resolved through the authorisation service's read-only API,
so that **every action anyone takes is checked against real, already set-up user data, whichever of the two populations they belong to**, and nothing can get through without going via the authorisation service. Updating that user data (roles, scope, or activation status) isn't done through this API at this stage — for now that happens by a database administrator running SQL directly, with a proper admin screen for it planned for later.

## Acceptance Criteria

1. Given `ctam-authorisation` is scaffolded as in Story 1.4.1, when the engineer adds the authorisation tables via the service-owned Liquibase change-set `db/changelog/001-init-auth-schema.sql`, then the six tables `ctam_auth_users`, `ctam_auth_staff_identities`, `ctam_auth_roles`, `ctam_auth_user_roles`, `ctam_auth_user_region_scopes`, and `ctam_auth_user_activation_flags` exist, with the structure set out in the architecture's data-tables reference; `ctam_auth_users` records `principal_kind` (JOH, staff, or service account) and links a JOH user to `ctam_joh_identities.id` via `joh_id` (with `ctam_joh_identities` in turn carrying the person's `personnel_number`), while an admin-staff user links instead to `ctam_auth_staff_identities.id` — both populations keyed on a CTAM-assigned unique identifier rather than any externally-supplied one; `ctam_auth_users` also records the user's jurisdiction; `ctam_auth_user_activation_flags` records the jurisdiction-and-region combination a user's activation status applies to; the `ctam_authorisation` database role owns all six tables, and has read-only access to the judicial reference data for identity look-ups; automated architecture checks in CI confirm that no other service ever writes to these tables.
2. Given the engineer implements the token-checking filter, following the shared authorisation pattern used across the programme, when a request arrives at any endpoint other than `/actuator/health`, `/actuator/readiness`, or `/actuator/info`, then the filter extracts the security token from the `Authorization: Bearer ...` header; checks its signature against the sign-in service's published keys (`ctam-mock-auth` for now, switching to the real HMCTS sign-in system ahead of the wider rollout, configurable via a Spring profile and secrets held in Key Vault); rejects any request without a valid token with `401 Unauthorized` and a standard (RFC 9457) problem-details error body; once the token checks out, calls the service's own `POST /authz/check` endpoint to work out who the person actually is; makes the result available to the rest of the request as a short-lived object that controllers and services can read.
3. Given an authenticated request reaches `POST /v1/authz/check` with a body `{"principal": "joh.test@example.justice.gov.uk"}` (a JOH user), when the email resolves against the judicial reference data, then the response is `200 OK` with a body containing `{"principal": "...", "canonicalId": "<ctam_joh_uuid>", "personnelNumber": "...", "population": "joh", "roles": [...], "jurisdiction": "...", "regions": [...], "areas": [...], "activated": true/false}`; the CTAM-assigned judicial identifier is the one carried forward as the person's canonical identity for the rest of the request; the personnel number is only ever used as the upstream look-up link.
4. Given an authenticated request reaches `POST /v1/authz/check` with a body `{"principal": "caseworker.test@example.justice.gov.uk"}` (an admin-staff user), when the email resolves against `ctam_auth_staff_identities`, then the response is `200 OK` with `{"canonicalId": "<staff-uuid>", "population": "staff", ...}` and exactly the same shape of roles, jurisdiction, scope, and activation information a JOH user gets back; roles and scope are worked out by joining `ctam_auth_users` to `ctam_auth_user_roles` and `ctam_auth_roles`, and separately to `ctam_auth_user_region_scopes`; the response includes the person's activation status for their specific jurisdiction-and-region combination, from `ctam_auth_user_activation_flags`.
5. Given a valid, correctly-signed token whose email matches neither the judicial reference data nor `ctam_auth_staff_identities`, when `POST /v1/authz/check` runs, then the person is rejected with a standard authorisation problem response — the same handling given to a user who exists but isn't yet activated; the rejection is logged with a correlation ID, and no account is automatically created.
6. Given an authenticated request reaches `GET /v1/users/{id}/effective-permissions`, when the caller is either looking up their own ID or holds a system-admin role, then the response is `200 OK` with a structured permissions document; if neither condition holds, the response is `403 Forbidden` with a standard problem-details body.
7. Given the API specification is generated by springdoc, when the engineer publishes it (via Gradle `maven-publish`) to the internal artefact repository, then `uk.gov.hmcts.ctam:api-ctam-authorisation:1.0.0` is available there; the standard API-spec lint passes on it; the specification uses `/v1/...`-style URL versioning; it declares the standard (RFC 9457) problem-details schema for error responses; the gateway's `Deprecation` and `Sunset` header policies for this API are documented.
8. Given the API gateway blocks `/actuator/*` paths from the outside, when an external caller attempts `GET /actuator/health` via the public gateway hostname, then the request is rejected at the gateway, and internal Kubernetes liveness and readiness checks still reach the pod directly.

## Dev Notes

### Context distilled from the bus

- `ctam_auth_users` is the shared principal table across both populations; `ctam_auth_staff_identities` is the CTAM-internal staff identity table (canonical identifier: CTAM-assigned UUID, architecture decision 2026-06-11, IdP email as the lookup key mirroring the JOH email → personnel-number pattern); `ctam_auth_roles`/`ctam_auth_user_roles`/`ctam_auth_user_region_scopes` carry roles and scope; `ctam_auth_user_activation_flags` carries the (jurisdiction, region) activation tuple for FR57's phased-activation cutover [Source: _arch/architecture/data-tables.md lines 116-121].
- FK convention: `joh_id` (uuid) → `ctam_joh_identities` is the CTAM-assigned canonical JOH identifier; `personnel_number` is stored only on `ctam_joh_identities` and is never a domain FK [Source: _arch/architecture/conventions.md#naming-patterns].
- The `JWTFilter` path is the only path: signature check against IdP JWKS, then `POST /authz/check`, populating request-scoped `AuthDetails` — never a second security mechanism, never a permit-all path [Source: _arch/agent-rules/50-security-and-logging.md#s9]. Roles, jurisdiction, Region/Area scope and the activation flag come from this service's own response, never read directly out of the JWT claims — the deliberate CTAM variance from the template's claims-only approach, and exactly what FR2/FR57 require [Source: _arch/agent-rules/50-security-and-logging.md#s10].
- RFC 9457 error taxonomy and status-code mapping (401 AuthN, 403 AuthZ, 422 validation, 409/412 the open optimistic-lock question — not relevant to this story's endpoints) are fixed centrally, not decided per-service [Source: _arch/architecture/conventions.md#format-patterns; _arch/agent-rules/30-api-contracts.md#c7].
- NFR13 ("Every API call resolves the principal's roles + Region/Area scope through the Authorisation service; no operation bypasses this check") is this story's architectural purpose, not an incidental property of it [Source: _arch/architecture/non-functional-requirements-coverage.md#security-nfr10-nfr16].
- FR-coverage-map attributes FR1 (sign-in + two-population identity resolution), FR2 (principal → roles + jurisdiction + Region/Area scope), FR3 (`GET /v1/users/{id}/effective-permissions`), and FR58 (API-as-Product read-side standards, first exercised here) to this story specifically [Source: _bmad-output/planning-artifacts/epics/fr-coverage-map.md, FR1/FR2/FR3/FR58 rows].
- The judicial reference-data lookup chain this story depends on (`jo_people` → `personnel_number` → `ctam_joh_identities`) is populated by Story 1.2.1's nightly eLinks sync, on the schema Story 1.1.2 created; this story reads that data read-only and never writes to it [Source: _bmad-output/planning-artifacts/epics/phase-1/epic-1.2-joh-reference-data-etl-process.md, Story 1.2.1 AC].

### Project Structure Notes

Repo assignment is unambiguous: every AC is either a schema change owned by the `ctam_authorisation` database role or an endpoint (`/authz/check`, `/effective-permissions`) that this service publishes. Standard per-service layering applies: `JWTFilter` and `AuthDetails` live in `config`; the two controllers in `controller`; identity/role/scope resolution logic in `service`; the read-only judicial-reference-data access is a direct JPA read per M16's documented exception, not a `client/` call.

### Out of scope / boundaries

- Endpoints for actually updating user roles, jurisdiction, region/area scope, or activation flags through this service — planned for after the initial rollout; for now a DBA runs SQL directly.
- Populating the six tables with real data — that is a later epic's seed scripts (dev/test) and a separate production identity-bootstrap process (epic-1.7), not writes through this API.
- Machine-to-machine authentication for automated external callers — out of scope for the whole epic, planned post-rollout.

### Definition of done

Per [`_arch/agent-rules/90-definition-of-done.md`](../../../_arch/agent-rules/90-definition-of-done.md), no deltas — this story carries real business logic (identity resolution, role/scope joins, the single-writer schema rule) and the full gate (coverage, mutation, Pact, Spectral, the six-table `*IT` suite) applies without exception. Note the open optimistic-lock status-code question (G6.7, `conventions.md` disagrees with itself on 409 vs 412) does not block this story — neither endpoint here performs a write — but do not resolve it opportunistically if it is noticed; it stays an open question for whichever story first hits it.
