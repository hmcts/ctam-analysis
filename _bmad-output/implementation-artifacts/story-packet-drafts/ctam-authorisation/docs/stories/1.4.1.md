# Story 1.4.1: Scaffold `ctam-authorisation` service from the HMCTS Crime SpringBoot template

Status: ready-for-dev

> **DRAFT — NOT DISPATCHED.** Authored ahead of the real dispatch flow because `ctam-authorisation` does not yet exist as a repo and this story's epic dependencies are not yet `done`. `sprint-status.yaml` still shows this story as `backlog`. Before this is real: confirm the repo exists, run `scripts/dispatch-preflight.sh 1.4.1`, re-verify `bus_version` against the repo's actual `_arch/` pin, then land it per delivery-operating-model.md's DISPATCH BRANCH step and flip `sprint-status.yaml` to `ready-for-dev` in the same change.

## Story

As a **platform engineer**,
I want to scaffold `ctam-authorisation` from HMCTS's standard Spring Boot starter template using the shared scaffolding script, connecting into the shared Azure environment already set up earlier,
so that **the authorisation service is built on the same consistent, secure, version-pinned foundation as every other service in the programme**, and the team can prove the whole deployment pipeline works end to end before any actual authorisation logic is written.

## Acceptance Criteria

1. Given the engineer has completed the GitHub manual set-up checklist (`ctam-architecture/runbooks/github-setup.md`) — an empty private `ctam-authorisation` repo created under the HMCTS org via the GitHub web UI, with branch protection enabled on `main` (PR review, status checks, linear history); and a clean local environment with Java 25, Gradle Wrapper, and Docker — when the engineer runs `ctam-scaffold.sh ctam-authorisation` from `ctam-architecture/scaffolding/`, then the script scaffolds a Spring Boot 4.0.x project locally from `https://github.com/hmcts/service-hmcts-crime-springboot-template` and commits/pushes it to the pre-created remote on a feature branch using plain `git` (no `gh`); the Gradle build uses the Groovy DSL with Spring Boot Gradle plugin 4.1.0 and `io.spring.dependency-management:1.1.7`; Group ID `uk.gov.hmcts.ctam`, artefact `ctam-authorisation`, base package `uk.gov.hmcts.ctam.authorisation`, default port 8082; the initial commit message reads exactly "Scaffold CTAM Pathfinder authorisation from HMCTS starter"; Lombok 1.18.46 and MapStruct 1.6.3 are configured; JJWT 0.13.0 and OWASP Encoder 1.4.0 are on the classpath; springdoc-openapi generates an OpenAPI 3.x spec; JaCoCo, CycloneDX SBOM, gradle-git-properties, gradle-versions, and gradle-docker-compose are configured; Spring Boot Test + JUnit 5 (`junit-bom:6.0.3`), Testcontainers PostgreSQL 1.21.4, Spring Boot Testcontainers 4.1.0, and spring-boot-starter-webmvc-test are configured; Spectral, ArchUnit, Spotless, and Checkstyle are configured; a Helm chart skeleton exists at `charts/ctam-authorisation/` with `values-dev.yaml`, `values-staging.yaml`, `values-production.yaml`; a `terraform/` skeleton exists with separate `dev`/`staging`/`production` stacks covering only this service's own cloud resources; GitHub Actions workflows exist at `.github/workflows/ci.yml`, `deploy-dev.yml`, `deploy-staging.yml`, `deploy-production.yml`; `CODEOWNERS` and `PULL_REQUEST_TEMPLATE.md` exist; a Postman collection skeleton exists at `postman/ctam-authorisation-phase0.postman_collection.json`.
2. Given the scaffolded service runs locally via `./gradlew bootRun` after `docker-compose up postgres`, when the engineer queries `http://localhost:8082/actuator/health`, then the response is `200 OK` with body `{"status":"UP"}`; `/actuator/info` returns Git metadata embedded by gradle-git-properties; `/actuator/readiness` returns `200 OK`; structured JSON logs via Logstash Logback Encoder 9.0 appear on stdout; logs include a `correlationId` populated by `CorrelationIdFilter` for each request.
3. Given the shared Azure environment (Kubernetes cluster, encrypted-at-rest PostgreSQL, container registry, API gateway, observability workspace, secrets vault) was already built and independently checked in `ctam-shared-infrastructure` as part of epic-1.0, when `ctam-authorisation` deploys, then it uses that shared cluster, database, registry, gateway, and observability workspace without building any of them again; `ctam-authorisation`'s own `terraform/` directory only ever creates its own resources (its Key Vault namespace, its API-gateway policy); its dev configuration's database connection string points at the shared encrypted PostgreSQL instance.
4. Given the shared `ctam_configuration_values` table was already created by the programme's baseline database change-log (epic-1.1, Story 1.1.1) ahead of the reference-data service being built, when `ctam-authorisation` is granted database access, then its database role has read-only (`SELECT`) access to `ctam_configuration_values`; and its own service-owned change-log directory (`src/main/resources/db/changelog/`, with a master file `db.changelog-master.yaml`) exists but is still empty — the actual authorisation tables are added in Story 1.4.3.
5. Given the deployed service is publicly reachable through the shared API gateway (built in epic-1.0), when an HTTP request reaches the gateway, then the connection terminates TLS using the latest TLS version the platform supports; plain HTTP requests are rejected and redirected to HTTPS; the gateway's TLS configuration is checked by a CI test using `testssl.sh` (or equivalent) in `ci.yml`, which fails if any TLS version below the platform's current minimum is still accepted.
6. Given the engineer pushes the initial commit to a feature branch and opens a Pull Request from that branch to `main` manually via the GitHub web UI (no `gh`), when the GitHub Actions `ci.yml` workflow runs, then it runs build, test, API-spec lint, architecture-rule checks, code-formatting checks, style checks, and a Helm chart lint; all checks pass on the scaffolded baseline; a code-coverage report is produced by JaCoCo.
7. Given the PR is merged to `main` via the GitHub web UI, when `deploy-dev.yml` triggers automatically, then the service deploys to the development Kubernetes cluster in UK South; the container image is pushed to Azure Container Registry; the deployed pod passes its liveness and readiness checks; Azure Application Insights receives structured log entries via the OpenTelemetry Collector.

## Dev Notes

### Context distilled from the bus

- Per-service Java structure is fixed, not invented per-service: `controller` / `service` / `repository` / `domain` / `dto` / `client` / `config` / `error` / `exception` under `src/main/java/uk/gov/hmcts/ctam/authorisation/`, with `src/main/resources/db/changelog/db.changelog-master.yaml` (empty for this story) [Source: _arch/architecture/conventions.md#structure-patterns].
- Table ownership prefix convention: any table this service later owns is `ctam_`-prefixed (`ctam_auth_users`, etc. — added in Story 1.4.3, not here) [Source: _arch/architecture/conventions.md#naming-patterns].
- The shared `ctam_configuration_values` table and its baseline changelog are owned by Story 1.1.1, run ahead of any service-specific migration; this story only needs read grant + an empty own changelog [Source: _bmad-output/planning-artifacts/epics/phase-1/epic-1.1-postgres-db-schema-design.md, Story 1.1.1 AC].
- TLS/transport: latest-TLS-only ingress, HTTP rejected/redirected, verified in CI — the architectural support for NFR10 [Source: _arch/architecture/non-functional-requirements-coverage.md#security-nfr10-nfr16].
- Structured logs + correlation IDs: this is the second service (after `ctam-reference-data`, Story 1.1.1) to exercise this pattern — NFR59's "every service story" clause [Source: _bmad-output/planning-artifacts/epics/fr-coverage-map.md, NFR59 row].
- Provenance of pinned scaffold tool versions (Checkstyle 14.0.0, Spotless Gradle plugin 8.10.0, JaCoCo 0.8.14, ArchUnit 1.5.0, pitest 1.25.9 etc.) was verified 2026-08-19 for the agent-rules pack itself; re-verify at scaffold time per R7 rather than trusting this citation as current [Source: _arch/agent-rules/index.md#provenance-of-pinned-tool-versions].

Repo assignment for this story is unambiguous: the epic's own vertical-slice text names `ctam-authorisation` explicitly as the service being scaffolded, and every AC operates entirely within that repo (its own `build.gradle`, its own Helm chart, its own `terraform/`). - Any actual authorisation logic — this story proves the pipeline, not the business behaviour.
- Provisioning the shared cluster, database server, registry, gateway, or observability workspace themselves — those are epic-1.0's responsibility; this story only connects to them.
