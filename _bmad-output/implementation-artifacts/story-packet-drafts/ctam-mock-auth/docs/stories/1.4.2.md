# Story 1.4.2: User can authenticate against `ctam-mock-auth` and receive a security token

## Story

As a **CTAM Pathfinder user from either identity population** (a JOH, or HMCTS admin staff — RSU, Court user, Tribunal Caseworker, Finance, or MI/Reporting),
I want to sign in against the stand-in sign-in service (`ctam-mock-auth`) in non-production environments using my email address,
so that **CTAM Pathfinder's development, automated testing, and user-acceptance testing can all proceed end to end before the real HMCTS sign-in system is connected**, while the token it issues has exactly the same shape as the one the real HMCTS system will issue once it's switched in.

## Acceptance Criteria

1. Given the engineer has manually pre-created the private GitHub repo `ctam-mock-auth` with branch protection on `main` via the GitHub web UI (per the runbook — the `gh` tool isn't available) and runs `ctam-scaffold.sh ctam-mock-auth`, when the scaffold completes, then the service has the same baseline as `ctam-reference-data` (Spring Boot 4.0.x, Helm chart, GitHub Actions, Actuator endpoints); the service implements the OIDC "authorization code" sign-in flow for human users; the service implements the OIDC "client credentials" flow for batch and scheduled components (used only by a later phase, but built now); a JWKS endpoint serves rotating signing keys at `/.well-known/jwks.json`; OIDC discovery information is served at `/.well-known/openid-configuration`.
2. Given `ctam-mock-auth` is starting up, when the Spring profile in use is `production`, then the application refuses to start with a fatal error message reading exactly "ctam-mock-auth must not be deployed to production"; and the production `deploy-production.yml` workflow is configured to never deploy `ctam-mock-auth`.
3. Given `ctam-mock-auth` is seeded with a test-user roster spanning both identity populations (JOH test users such as `joh.test@example.justice.gov.uk` and `tribunal.member.test@example.justice.gov.uk`; admin-staff test users such as `caseworker.test@example.justice.gov.uk` and `rsu.test@example.justice.gov.uk`), when a user navigates to the OIDC sign-in endpoint with valid client and redirect parameters, then they see a development-mode login screen (no real password — pick identity by email from a seeded list, with a banner reading "Development authentication only — not for production"); after selection they're redirected back with an authorisation code; that code can be exchanged for an ID token and access token via the token endpoint; the returned token contains the standard OIDC claims (`sub`, `email`, `iss`, `aud`, `exp`, `iat`); the token's signature validates against the JWKS endpoint.
4. Given a service-token client `ctam-payment-batch-client` is seeded in `ctam-mock-auth`, when a "client credentials" grant is requested with valid client credentials, then a service-principal token is returned carrying claims that identify the client, and that token also validates against the same JWKS endpoint.
5. Given `ctam-mock-auth` is deployed to the development Kubernetes cluster, when an unauthenticated request reaches a discovery URL, then the response is `200 OK` (discovery information is public); and every other endpoint requires a valid token and returns a standard (RFC 9457) problem-details error on failure.

## Dev Notes

### Context distilled from the bus

- Service-principal authentication is the documented pattern for batch/scheduled components with no upstream user; in non-prod the client store is `mock_oauth_clients` on `ctam-mock-auth`, and the MVP-relevant client is `ctam-payment-batch` [Source: _arch/architecture/conventions.md#communication-patterns].
- JWT propagation and the `client_credentials` service-principal pattern together satisfy NFR12 ("All human users authenticated via HMCTS IdP SSO... inter-service authentication for batch/scheduled components is via OAuth 2.0 client_credentials against ctam-mock-auth in non-prod") [Source: _arch/architecture/non-functional-requirements-coverage.md#security-nfr10-nfr16].
- `mock_` is a dedicated, dev-only table prefix, exempt from the `ctam_` ownership rule precisely because it is never deployed to production — `mock_oauth_clients`, `mock_user_roster` [Source: _arch/architecture/conventions.md#naming-patterns; _arch/architecture/data-tables.md line 197].
- S12 makes explicit what AC-2 requires structurally, not just by convention: "`ctam-mock-auth` and the `mock_*` tables are dev/CI only. No production profile, Helm value, or default configuration may reference them, and no code path may fall back to them when the real issuer is unreachable." [Source: _arch/agent-rules/50-security-and-logging.md#s12].
- Every downstream `JWTFilter` (in `ctam-authorisation` and every other service) validates against this service's JWKS the same way it will later validate against the real HMCTS IdP — switching issuers is meant to be a configuration change, not a rebuild, per the epic's own framing.

### Rules that apply

Per the agent-rules index, `ctam-mock-auth` is one of the twelve Java execution units the pack fully covers — the complete rule set applies, the same as any other Spring Boot service [Source: _arch/agent-rules/index.md#who-this-binds].

- [`_arch/agent-rules/00-core.md`](../../../_arch/agent-rules/00-core.md) — R1, R2/T1, R6 (no unsanctioned surface — the seeded roster and clients are exactly what the story calls for, nothing more), R11 (never log a token, client secret, or the seeded users' emails at anything but the correlation-id level).
- [`_arch/agent-rules/10-tdd.md`](../../../_arch/agent-rules/10-tdd.md) — T7 (one Spring context test budget — the profile-guard startup-failure test is a legitimate use of it), T12 (no wall clock — `exp`/`iat` claims are computed from an injected `Clock`, never `Instant.now()` directly).
- [`_arch/agent-rules/20-modularity.md`](../../../_arch/agent-rules/20-modularity.md) — standard layering; the OIDC endpoints live in `controller`, token issuance and JWKS rotation logic in `service`.
- [`_arch/agent-rules/30-api-contracts.md`](../../../_arch/agent-rules/30-api-contracts.md) — C7 (RFC 9457 on every failure path, including the unauthenticated-endpoint case in AC-5).
- [`_arch/agent-rules/50-security-and-logging.md`](../../../_arch/agent-rules/50-security-and-logging.md) — S1 (never log a JWT, the `Authorization` header, or a client secret), S6 (JWKS signing keys and the `ctam-payment-batch-client` secret resolve through Key Vault, never a fixture file committed to the repo), S7 (test credentials must be self-evidently synthetic), S12 (this service structurally cannot reach production).

### Project Structure Notes

Repo assignment needed a closer read, as flagged: story 1.4.2's AC set is entirely about implementing `ctam-mock-auth` itself — scaffolding it, wiring its OIDC endpoints, seeding its roster, refusing to boot on the `production` profile. Nothing in the ACs describes a consuming service's integration test; the "user authenticates" framing is the human-facing behaviour of this service's own sign-in screen. That places the whole story inside `ctam-mock-auth`, not as an integration-test story in `ctam-authorisation` or `ctam-ui` (those repos' own consumption of this service is covered separately — the `JWTFilter`/`/authz/check` side in Story 1.4.3, the `HmctsIdpProvider` wrapper in Stories 1.4.4/1.4.5).

Standard per-service Java structure applies [Source: _arch/architecture/conventions.md#structure-patterns]: OIDC/JWKS endpoints in `controller`, token issuance and roster/client seeding in `service`, no `domain`/`repository` beyond the `mock_*` seed tables this story needs.

### Out of scope / boundaries

- Resolving a signed-in user's roles, jurisdiction, or region/area scope — that is `ctam-authorisation`'s `/authz/check`, Story 1.4.3, not this service.
- The `HmctsIdpProvider` React wrapper and the browser-side sign-in flow — Stories 1.4.4/1.4.5, in `ctam-ui`.
- Connecting to the real HMCTS sign-in system — out of scope for the whole epic; this story only builds and exercises the stand-in.
