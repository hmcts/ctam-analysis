# Story 1.0.5: The API gateway is built and checked end to end (development environment)

Status: ready-for-dev

## Story

As a **platform engineer**,
I want the API gateway built through Terraform, with baseline security policies and a simple test API, so it can be proven working end to end,
so that **the shared public-facing gateway is proven to handle encrypted traffic and correctly route it into the cluster, before any real service publishes an API through it**.

## Acceptance Criteria

1. Given the cluster exists as described in Story 1.0.2, when the engineer adds the gateway setup and applies it to the development environment, an API gateway is provisioned, with a resilient setup and baseline policies in place — encrypted connections terminated at the latest supported security level, a tracking identifier passed through on every request, and sensible default limits on how many requests can be made.
2. A simple test API is registered on the gateway, pointing at a basic echo service running inside the cluster.
3. Any request made over an unencrypted connection is rejected or automatically redirected to an encrypted one.
4. Given the gateway and the test API have been set up, when the engineer calls the test operation through the gateway, the call succeeds over an encrypted connection and gets a response back from the echo service running inside the cluster, confirming the whole path from the outside world into the cluster works end to end.
5. A request made using a connection weaker than the platform's minimum accepted security level is correctly refused, checked automatically as part of the pipeline.
6. A call made to a protected route without the right credentials is correctly rejected.
7. These checks are written down as repeatable verification steps.
8. Given all five layers have now been built, when the engineer reviews the finished development environment, the complete shared estate — cluster, database, secrets vault, registry, monitoring, and gateway — exists in the UK South region, with every layer independently checked and proven working.
9. The platform is ready for the team building the judicial reference-data service to set up their own service and deploy it onto this foundation.

## Tasks / Subtasks

- [ ] Task 1 (AC: 1): Write `terraform/modules/apim/` (instance + base policies: TLS termination at the latest supported level, correlation-ID passthrough, default rate limiting).
- [ ] Task 2 (AC: 2): Deploy a basic echo service into the cluster and register it as a test API on the gateway.
- [ ] Task 3 (AC: 3): Configure the gateway policy to reject or redirect any plaintext-HTTP request.
- [ ] Task 4 (AC: 4, 7): Write `verification/apim-smoke.sh`'s happy-path half — call the test operation through the gateway over TLS and confirm the echo response. Capture red (before the module exists — no route resolves) then green.
- [ ] Task 5 (AC: 5, 7): Extend `verification/apim-smoke.sh` with a `testssl.sh`-driven check (per the script's stated purpose in the repo-structure inventory) that a connection below the platform's minimum TLS floor is refused, run automatically in the pipeline.
- [ ] Task 6 (AC: 6, 7): Extend `verification/apim-smoke.sh` to confirm a protected route rejects a call with no/invalid credentials.
- [ ] Task 7 (AC: 8, 9): With Stories 1.0.1–1.0.5 all applied to dev, do a final review pass confirming all six pieces of the estate (repo/CI, cluster, database, vault, registry, monitoring, gateway) exist in UK South and each has its own passing verification script — this is the epic-closing checkpoint, not a new resource to build.
