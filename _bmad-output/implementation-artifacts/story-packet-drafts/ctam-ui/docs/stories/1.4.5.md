## Story

As a **CTAM Pathfinder user from either identity population** (a JOH or an admin staff member),
I want to sign into CTAM Pathfinder through single sign-on, have my confirmed identity, roles, jurisdiction, and region/area scope worked out, and land on a Home page whose navigation and information tiles match what I'm allowed to do,
so that **I can start using CTAM Pathfinder's day-to-day workflows** — and, by the end of this phase, the whole pattern can be demonstrated working end to end: signing in through the stand-in sign-in service, resolving against judge and tribunal-member data kept up to date by the nightly sync, being authorised, and reaching the web application.

## Acceptance Criteria

1. Given the user opens `ctam-ui` while not signed in, when they navigate to any protected page, then the protected-route guard redirects them to the single-sign-on flow at the stand-in sign-in service (in non-production environments); the user completes the development-mode login (selecting their seeded test identity — JOH or admin staff); they're redirected back to `ctam-ui` with an authorisation code in the URL; the HTTP client exchanges that code for an ID token and access token; the user is redirected to `/home`.
2. Given the user is signed in, when the Home page renders, then the page shows a header with the CTAM Pathfinder brand, the user's name, a sign-out button, and a region/area selector populated with the regions and areas the person is authorised for (resolved, together with their identity and jurisdiction, through the authorisation service's check endpoint); the primary navigation shows only the links the user's roles authorise (for example, a JOH sees "My Itinerary" and "Request Absence" but not operational admin workflows, while a Tribunal Caseworker or RSU Admin sees the operational workflows); the page shows placeholder summary tiles (JOH count, pending absences, vacancies, payments — all showing "—" or "loading" at this stage); a contextual help link is present in the footer.
3. Given the user is signed in, when they click sign-out, then the sign-out flow runs against the stand-in sign-in service; the user is redirected back to `ctam-ui` and lands on an unauthenticated landing page; the access token and refresh token are cleared from client storage.
4. Given the user's activation record shows their jurisdiction-and-region combination hasn't gone live on CTAM Pathfinder yet, when they land on Home, then they see a banner reading exactly "Your jurisdiction/region has not yet moved to CTAM Pathfinder. Please continue using your current system," and the workflow navigation is disabled.
5. Given the automated accessibility scan runs on the rendered Home page, when the page is in a steady state, then no new WCAG 2.2 AA violations are reported; keyboard navigation works through the header, the region/area selector, the primary navigation, and the tiles; focus indicators are visible throughout.
6. Given the end-to-end test suite for this phase runs, when `tests/e2e/phase-1-foundation.spec.ts` executes, then it covers: an unauthenticated user being redirected → signing in via the stand-in service (one JOH user and one admin-staff user) → Home rendering with role-scoped navigation → the activation banner showing for a not-yet-activated jurisdiction/region → the sign-out flow; all assertions pass against the development deployment.
7. Given this phase's demonstration milestone, when the engineering lead runs the walkthrough, then they can show a stakeholder the whole chain working together — platform foundations, JOH/MRD data flowing in, the authorisation service scaffold, signing in via the stand-in service, authorisation correctly enforced for both populations, the web application foundation, and the complete end-to-end sign-in flow; and the Postman collection `ctam-authorisation-phase0.postman_collection.json` exercises `POST /v1/authz/check` (for both populations, and for an unresolvable principal) and `GET /v1/users/{id}/effective-permissions`, run against the development deployment.

## Dev Notes

### Context distilled from the bus

- This story is the end-to-end proof point for NFR12 (human users authenticated via HMCTS IdP SSO, per FR1) and the region/area-scoped, role-based navigation FR55 calls for [Source: _arch/architecture/non-functional-requirements-coverage.md#security-nfr10-nfr16; _bmad-output/planning-artifacts/epics/fr-coverage-map.md, FR1/FR55 rows].
- NFR1 sets the Home page's static-load budget (≤3s initial render) — the only performance NFR this story's AC set plausibly touches, since the tiles are placeholders and no federated read (NFR8) happens yet [Source: _arch/architecture/non-functional-requirements-coverage.md#performance-nfr1-nfr9].
- Accessibility architectural support (axe-core in CI, GOV.UK Design System, React Hook Form) is the same NFR17–19 basis cited in Story 1.4.4; this story is where it is exercised against real signed-in content rather than a static shell [Source: _arch/architecture/non-functional-requirements-coverage.md#accessibility-nfr17-nfr19].
- Loading-state convention (`isLoading`/`isFetching`/`isError` via TanStack Query, GOV.UK loading patterns, no ad-hoc spinners) governs how the placeholder tiles must render while "loading" [Source: _arch/architecture/conventions.md#process-patterns].
- The role-scoped navigation and region/area selector are populated entirely from the authorisation service's `/authz/check` response (Story 1.4.3) — `roles`, `jurisdiction`, `regions`, `areas`, `activated` — never derived independently in the UI from the raw JWT, consistent with S10's "never trust a claim for an authorisation decision" even though that rule is written for the Java stack; the same principle governs this UI story (do not decode and trust JWT claims client-side for role-gating; trust the resolved response) [Source: _arch/agent-rules/50-security-and-logging.md#s10].
- The demonstration milestone (AC-7) is the epic's own stated proof that the whole vertical slice — 1.4.1 through 1.4.5, plus the epics it depends on — works together; the Postman collection referenced is the same artefact scaffolded in Story 1.4.1 and exercised for its endpoints in Story 1.4.3.

### Project Structure Notes

Repo assignment needed a closer read, as flagged: this story's ACs are entirely about `ctam-ui` rendering behaviour (the Home page, the sign-out flow, the activation banner) and a `tests/e2e/` spec file — the same `tests/e2e/phase-1-foundation.spec.ts` file Story 1.4.4 starts, extended here. Nothing in the ACs describes new back-end endpoint behaviour (that is Stories 1.4.2/1.4.3); this is the UI-and-E2E consumption of those already-built APIs, so it belongs in `ctam-ui`, matching the epic's own "lands on a Home page" framing and the `conventions.md` UI repo structure's `tests/e2e/` location for this exact spec file.

Expected layout: the Home route and its components live under a shared/top-level location (not a `modules/{domain}/` folder, since Home is cross-cutting shell, not a single business domain) — `src/shared/components/` for the header/nav/tile-shell pieces reused from `PageLayout` (Story 1.4.4), with a `Home`-specific page component; `tests/e2e/phase-1-foundation.spec.ts` extended in place per [Source: _arch/architecture/conventions.md#structure-patterns].

### Out of scope / boundaries

- Real figures behind the summary tiles (JOH count, pending absences, vacancies, payments) — those land once the relevant business-domain features are built in later phases.
- The full process for switching a jurisdiction/region on — planned for much later in the programme; this story only renders the banner when a user's activation flag says "not yet."
- Which incumbent system a not-yet-activated user should keep using is not resolved here for ET (tracked as the placeholder `[ET-INCUMBENT-TBD]`, per G8.4) — the banner text is fixed and generic across jurisdictions; it does not name a specific incumbent system.
- Machine-to-machine / service-principal sign-in — out of scope for this human-facing story.
