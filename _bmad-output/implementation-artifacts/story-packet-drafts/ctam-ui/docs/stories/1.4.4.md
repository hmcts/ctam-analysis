## Story

As a **front-end engineer**,
I want to scaffold the `ctam-ui` public-facing web application with all of CTAM Pathfinder's shared conventions built in — sign-in, the design system, a shared way of talking to the back end, accessibility checks in CI, and end-to-end tests,
so that **every screen built for each business area over the following phases lands on a stable, checked, accessible foundation**, rather than each phase inventing its own approach from scratch.

## Acceptance Criteria

1. Given the engineer has manually created the private GitHub repo `ctam-ui`, with branch protection on `main`, through the GitHub web UI (repo creation, branch protection, team access, and CODEOWNERS set-up are all manual web-UI steps, since `gh` isn't available), and sets up the repo locally from a Vite React-and-TypeScript template and pushes it via plain `git push` to the pre-created remote, when scaffolding completes, then the repo uses React, TypeScript, Vite, Vitest (unit tests), and Playwright (end-to-end tests); the repo is private, under the HMCTS organisation, with branch protection on `main`; its dependencies include the GOV.UK Design System base plus HMCTS and CTAM Pathfinder's own extensions; TanStack Query is configured to manage the lifecycle of requests to the back end; tooling is set up to automatically generate client code from each back-end service's published API specification, placing the generated code into `src/modules/{domain}/api/` for each business area.
2. Given the engineer implements the sign-in wrapper in `src/shared/auth/`, when the wrapper is complete, then `HmctsIdpProvider.tsx` exposes the OIDC sign-in context, configurable per environment (pointing at `ctam-mock-auth` in development and CI, and at the real HMCTS sign-in system in later environments); `ProtectedRoute.tsx` redirects unauthenticated users into the single-sign-on flow; `useAuth.ts` exposes `{ user, isLoading, isAuthenticated, signIn, signOut }`; the shared HTTP client in `src/shared/api/httpClient.ts` attaches `Authorization: Bearer ...` to every authenticated request; `src/shared/api/errorHandling.ts` translates standard (RFC 9457) problem-details error responses into UI-ready error structures, with a title, a detail message, and field-level errors where present.
3. Given the engineer wires up the design-system foundation, when the foundation is complete, then the GOV.UK Design System base CSS is loaded; HMCTS and CTAM Pathfinder design tokens (colours, spacing, typography) are applied; a `<PageLayout>` component exposes a header, a primary-navigation slot, a region selector slot, a main content slot, and a footer; the layout is responsive across mobile, tablet, and desktop screen sizes.
4. Given the engineer sets up accessibility checks in CI, when the automated accessibility scan (axe-core) runs as part of `ci.yml`, then the build fails on any new WCAG 2.2 AA violation; keyboard navigation is verified by a Playwright smoke test (tab order through the navigation, with a visible focus indicator); screen-reader-relevant ARIA labels are present on tabbed and dynamic content.
5. Given the engineer publishes the first end-to-end test suite, when `tests/e2e/phase-1-foundation.spec.ts` runs in CI, then the suite verifies the app starts, redirects unauthenticated users to the stand-in sign-in service, and renders a placeholder landing route once signed in — following the shared end-to-end testing pattern used across the programme.
6. Given the engineer sets up deployment, with the Azure Static Web App resource provisioned by Terraform code living in this repo's own `terraform/` directory (the first repo in the programme that needs this particular kind of cloud resource), when the pull request is merged, then the built application is deployed to that Terraform-provisioned Azure Static Web App, in the UK South development environment; this deployment is entirely independent of any future separate admin-only web application, which isn't part of this initial rollout; the development hostname (configurable in production to become `ctam.hmcts.gov.uk`) resolves to the new deployment.

## Dev Notes

### Context distilled from the bus

- UI repo structure is fixed: `src/modules/{domain}/` (pages/components/hooks/api/index.ts per business area) plus `src/shared/{components,hooks,auth,api}/` and `src/styles/`; module-per-domain, not by-type, because each domain phase's UI work should be one folder [Source: _arch/architecture/conventions.md#structure-patterns].
- JSON/date/error-envelope conventions the generated API clients and `errorHandling.ts` must honour: camelCase fields, ISO 8601 dates, RFC 9457 `application/problem+json` on every error response [Source: _arch/architecture/conventions.md#format-patterns].
- Loading-state and form-validation UI conventions are fixed centrally: TanStack Query's `isLoading`/`isFetching`/`isError`, GOV.UK Design System loading patterns (no ad-hoc spinners); React Hook Form + Zod schemas matching the OpenAPI request shape, server remains the source of truth [Source: _arch/architecture/conventions.md#process-patterns].
- Accessibility architectural support for this story is exactly axe-core in CI (Vitest + Playwright runs) plus the GOV.UK Design System component library and React Hook Form — WCAG 2.2 AA (NFR17), assistive-technology compatibility (NFR18), and the Public Sector Bodies Accessibility Regulations 2018 (NFR19) [Source: _arch/architecture/non-functional-requirements-coverage.md#accessibility-nfr17-nfr19].
- FR56 splits into a business stack (`ctam-ui`, delivered in this phase) and an admin stack (`ctam-admin-ui`, explicitly post-MVP) — this story is the business-stack half [Source: _bmad-output/planning-artifacts/epics/fr-coverage-map.md, FR56 row].
- `HmctsIdpProvider` must point at `ctam-mock-auth` in dev/CI and the real HMCTS IdP later purely by environment configuration — this is the same "switching over is a config change, not a rebuild" principle the epic states for the back-end sign-in service.
