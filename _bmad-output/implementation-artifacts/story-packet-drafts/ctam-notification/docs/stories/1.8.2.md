# Story 1.8.2: The "send an email" endpoint delivers, retries, and logs every request, with a way to review what was sent

Status: ready-for-dev

## Story

As a **calling service** (for example, the later work that acknowledges an absence request or confirms a booking, both triggered by a signed-in user's own action),
I want a single endpoint that accepts a template, a recipient, and the data to fill it with, checks that the caller is a genuine signed-in user, records the attempt, sends the email with automatic retries if something temporarily goes wrong, and gives a clear, standard error response if the request is invalid,
so that **sending a transactional email is a single, dependable, observable action** that every later, user-triggered feature can use in exactly the same way. A way for fully automated, unattended processes to call this same endpoint is intentionally left for later in the programme, once the first such process (an automated payment run) actually needs it.

## Acceptance Criteria

1. **Given** the notification service has been set up as described in the previous story, **when** the engineer builds the send endpoint, **then** `POST /v1/notifications/send` accepts a request containing a template identifier, a recipient, and a data payload, **and** the endpoint only accepts requests carrying a genuine signed-in user's identity, passed through from the calling service, **and** the calling user's role is checked against who is allowed to trigger that particular template (for example, in this phase only the roles responsible for absence handling, plus system administrators, may trigger the absence-acknowledgement email), **and** on a valid request, a new row is recorded in the delivery-history table with status "queued" and the triggering user's identity attached, and the caller receives back an acknowledged-and-queued response along with a reference id for that delivery.
2. **Given** a background process regularly checks for queued rows, picking each one up safely so that two processes never work on the same row at once, **when** it picks up a row, **then** it marks that row as "sending", **and** attempts to send the actual email, **and** on success, marks it "sent" and records when it was sent, **and** on a temporary failure, records the attempt and the error, and puts it back in the queue to try again — up to five attempts in total, waiting progressively longer between each, **and** once all five attempts are used up, marks it as given-up-on, keeping the last error visible for someone to investigate.
3. **Given** an invalid request reaches the send endpoint, **when** something required is missing or malformed — the template, the recipient, or the data payload, **then** the response is a clear, standard "bad request" error explaining exactly which field was wrong, **and** nothing is recorded in the delivery-history table.
4. **Given** a request reaches the send endpoint without a genuine signed-in user's identity attached, **when** that identity is missing or cannot be verified, **then** the response is a clear, standard "not authenticated" error, **and** nothing is recorded in the delivery-history table.
5. **Given** a request arrives claiming to be from a fully automated, unattended process rather than a signed-in user, **when** the service checks its identity, **then** the request is turned away with a clear, standard error explaining that automated callers are not supported yet, and that this capability will arrive later in the programme once the first such caller needs it, **and** that rejection is itself logged, so the attempt remains visible.
6. **Given** a delivery-history lookup endpoint is added, **when** it is called by someone with a system-administrator role, **then** it returns the delivery history, page by page, filterable by recipient, status, date range, or triggering user, **and** anyone without that role is turned away with a clear, standard "not allowed" error.
7. **Given** the service's published description of how to call it is regenerated, **when** the new version is published, **then** it passes the programme's standard documentation-quality check, **and** it documents both the send endpoint and the delivery-history lookup endpoint, **and** it clearly notes that support for fully automated callers is intentionally left for a later version, and that only signed-in-user calls are supported for now.
8. **Given** a ready-made set of test requests for this service is published, **when** it is run automatically as part of the build, **then** it covers: the normal successful path; a bad request; a not-authenticated request; an admin-only check on the history lookup; an automated-caller request being correctly turned away; and the retry behaviour, using a removable test-only endpoint that deliberately triggers a failure, **and** the hands-on check for this phase is: open the testing tool, sign in as a test user, send a request, watch the delivery-history entry move to "sent", then open the email stand-in tool and confirm the email rendered correctly. (There is no admin screen for this check in this phase.)

## Dev Notes

### Context distilled from the bus

- **Endpoint contract.** `POST /v1/notifications/send` is the one named endpoint on the bus for this epic; conventions fix its shape: resources are plural nouns, actions are URL segments, request/response bodies are `camelCase` JSON, and DTOs are separate immutable records per direction (never a shared or entity type). [Source: _arch/architecture/conventions.md — "Naming Patterns" → API endpoints; "Format Patterns"; _arch/agent-rules/30-api-contracts.md#c11]
- **Errors are fixed-taxonomy RFC 9457.** 400 is parser-level malformed input; 422 is a well-formed request that fails validation or a business rule (C9) — AC-3's "missing or malformed" field errors are 422 `validation`, not 400, unless the JSON itself cannot parse. 401 is `Unauthorized` (AC-4, missing/unverifiable identity); 403 is `Forbidden` with `type` category `authorisation` (AC-1's per-template role check, AC-6's admin-only history lookup). [Source: _arch/architecture/conventions.md — "Format Patterns" → HTTP status codes; "Communication Patterns" → Error categorisation taxonomy; _arch/agent-rules/30-api-contracts.md#c7, #c9]
- **AC-5's "automated caller" rejection has no dedicated problem-type category on the bus.** The fixed taxonomy is `validation` / `authorisation` / `business-rule` / `dependency` / `data` / `concurrency` / `unexpected` — there is no "capability not yet available" category, and C8 requires a cited convention or a human decision before inventing one. This packet's working decision, to confirm against C1's contract-first step before coding: treat the rejection as an authorisation failure (`403`, `type` category `authorisation`) via a custom exception, since the substance of the rejection is "this principal kind is not permitted to call this endpoint yet" — the same shape as any other role check on this endpoint, not a new category. If the implementing session disagrees, this is exactly the kind of call R5 says to stop and record, not silently pick. [Source: _arch/agent-rules/30-api-contracts.md#c7, #c8; _arch/architecture/conventions.md — "Communication Patterns" → Error categorisation taxonomy]
- **AC-1's "acknowledged-and-queued response along with a reference id" has no exact match in the fixed status-code table either** — the table lists 200/201/204/400/401/403/404/409/422/429/5xx, with no 202. This packet's working decision: use `201 Created` (a delivery-history row is in fact created) with the dispatch id in the response body; omit a `Location` header, since this story defines no single-resource `GET /v1/notifications/dispatches/{id}` route (only the paginated lookup in AC-6) and inventing one would be unsanctioned surface (R6). Confirm this against C1 before implementing. [Source: _arch/architecture/conventions.md — "Format Patterns" → HTTP status codes; _arch/agent-rules/00-core.md#r6]
- **Authorisation never reads a role from the JWT.** Both the per-template role check (AC-1) and the admin-only history lookup (AC-6) must resolve the caller's role from `AuthDetails` (populated by the per-service `JWTFilter` calling `ctam-authorisation`'s `/authz/check`), never from a JWT claim directly. [Source: _arch/agent-rules/50-security-and-logging.md#s9, #s10, #s11]
- **JWT propagation only — no `client_credentials` in this story.** This epic is explicit that only signed-in-user calls are supported at Phase 1; the bus documents `client_credentials` as the pattern for batch/scheduled callers (the MVP case being `ctam-payment-batch`), which is out of scope here and moves to a later phase. AC-5 exists precisely to turn that caller kind away for now, not to implement it. [Source: _arch/architecture/conventions.md — "Communication Patterns" → "Inter-service authentication at MVP — two patterns"]
- **Retry is a service-internal concern, not an inbound-retry policy.** C14 ("retry only what is safe... a non-idempotent POST is never retried automatically") governs *outbound* client calls this service makes to other services; AC-2's five-attempt backoff is this service's own retry of its outbound send to the HMCTS email system, which is exactly the kind of idempotent-operation retry C14 sanctions, implemented in the notification service's own send path rather than any generic idempotency-key mechanism (which is prohibited outright). [Source: _arch/agent-rules/30-api-contracts.md#c14; _arch/agent-rules/40-data-and-liquibase.md#p14]
- **Safe row pickup uses native constructs only** — no idempotency-key table, no application-level or advisory locking. The version marker on the table (from Story 1.8.1) is `@Version` optimistic locking; a pessimistic row lock is the documented alternative for a cross-row queue scan. [Source: _arch/agent-rules/40-data-and-liquibase.md#p14]
- **Time is always via the injected `Clock`.** `sent_at`, `last_attempted_at`, and the backoff calculation must never call `Instant.now()`/`LocalDateTime.now()` directly. [Source: _arch/agent-rules/20-modularity.md#m20; _arch/agent-rules/40-data-and-liquibase.md#p15]
- **Pagination for the history lookup.** AC-6 is a small, filtered list (recipient/status/date-range/user), which the bus's pagination convention places in the offset-based `?page=&size=` family, not the cursor family used for large chronological lists. [Source: _arch/architecture/conventions.md — "Format Patterns" → Pagination]
