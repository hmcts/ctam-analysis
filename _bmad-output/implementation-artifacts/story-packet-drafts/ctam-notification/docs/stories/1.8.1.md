# Story 1.8.1: The notification service, its delivery-history table, and its connection to email are set up

Status: ready-for-dev

## Story

As a **platform engineer**,
I want to set up the notification service following the programme's established pattern, create the table that will record every email attempt, and connect the service to the HMCTS email system,
so that **the later features that need to send email** (acknowledging an absence request, confirming a booking, and eventually payment notifications) **can rely on a consistent, ready-made way of doing so from the very start**, rather than each one building its own.

## Acceptance Criteria

1. **Given** the engineer has manually created the notification service's own private code repository, with the standard protections on its main branch, following the same manual set-up process already used for the platform's very first services, **and** runs the standard scaffolding script for it, **when** the scaffolding completes, **then** the new repository has the same baseline as every other service built so far — the standard application framework, deployment packaging, automated build pipeline, health checks, structured logging, API documentation tooling, and code-quality checks — **and** it is registered under the group `uk.gov.hmcts.ctam`, named `ctam-notification`, using the package `uk.gov.hmcts.ctam.notification`, and defaults to port 8082, **and** the very first commit is recorded as *"Scaffold CTAM Pathfinder notification from HMCTS starter"*.
2. **Given** the engineer adds the database change that creates the delivery-history table, **when** that change is applied, **then** a `ctam_notification_dispatches` table exists, recording for every email attempt: a unique id, which template was used, who it was sent to, what data it contained, its status (queued, sending, sent, failed, or given up on), how many attempts have been made, when the last attempt happened, what the last error was (if any), when the record was created, when it was actually sent, which signed-in user's action triggered it (for audit purposes), and a version marker used to prevent two processes updating the same record at once, **and** the table is owned by the notification service's own database role, **and** its structure is documented alongside the rest of the programme's database documentation.
3. **Given** the engineer configures the connection to the email system, **when** the service starts up in a development environment, **then** its email settings are loaded from the environment's configuration and from the programme's secure secret storage, **and** in every non-production environment, a safe local stand-in for the real email system intercepts anything the service tries to send, so no real emails ever go out during testing, **and** in production, the same configuration points at the real HMCTS email system.
4. **Given** the service is deployed to the development environment, **when** its health-check address is queried, **then** it responds successfully, including the current health of its connection to the email system, **and** it reports itself as degraded if that email connection cannot be reached.

## Dev Notes

### Context distilled from the bus

- Scaffolding defaults are fixed, not a choice for this story: group `uk.gov.hmcts.ctam`, artefact `ctam-{service-name}`, package `uk.gov.hmcts.ctam.{service-name}`, default port `8082`, and the exact first-commit message pattern `"Scaffold CTAM Pathfinder {service-name} from HMCTS starter"`. [Source: _arch/architecture/starter-template.md — "Per-service CTAM Pathfinder Conventions" and the "Initial commit on new repo" snippet]
- The base HMCTS starter is deliberately minimal (actuator, observability, logging only); the build pipeline, structured logging detail, DB/security/Azure patterns are added by `ctam-scaffold.sh` cherry-picking from `hmcts/service-hmcts-springboot-demo`, not present in the base template. [Source: _arch/architecture/starter-template.md — "Architectural Decisions: Base Template vs CTAM Scaffolding Overlay"]
- `ctam_notification_dispatches` is already inventoried as the service's one table: "Outbound email dispatch log (recipient, content type, dispatched-at, status, retry count, FR9)". [Source: _arch/architecture/data-tables.md — "Notification service (`ctam-notification`) — 1 table"]
- Table/column naming: `ctam_` prefix (CTAM-owned), `snake_case` columns, `uuid` PK named `id`, audit columns `created_at`/`updated_at timestamptz NOT NULL` (this table also needs `sent_at` for the epic's "when it was actually sent", which is a domain column, not the audit pair). [Source: _arch/architecture/conventions.md — "Naming Patterns" → Database]
- The "version marker used to prevent two processes updating the same record at once" in AC-2 is `@Version` optimistic locking — one of the three native concurrency constructs this programme allows (natural-key unique constraint, `@Version`, pessimistic row lock); no idempotency-key tables, no application-level or advisory locking. [Source: _arch/agent-rules/40-data-and-liquibase.md#p14 — "Concurrency uses native constructs only"]
- Secrets (the SMTP/HMCTS email connection details) resolve only through Spring Cloud Azure Key Vault — never `application*.yml`, a Helm value, or a test fixture; if the story seemed to need a secret in a file, that would be a stop. [Source: _arch/agent-rules/50-security-and-logging.md#s6]

### Rules that apply

- `_arch/agent-rules/00-core.md` R1–R14 — read in full before the first edit; R2 (red before green), R6 (no unsanctioned surface: this story adds exactly one table and the mail config, nothing more), R9 (modularity limits are non-negotiable).

- `_arch/agent-rules/50-security-and-logging.md` S1/S2 (a delivery record legitimately stores the recipient address and template data, but log lines about it must never print the row — log `dispatch_id`/`correlation_id` only, never the recipient or payload), S6 (Key Vault only for the email connection), S8 (TLS to the email system at 1.3 minimum, 1.2 fallback — no `trustAll` in any profile).

### Out of scope / boundaries

From the epic's "Explicitly out of scope (left for later phases)" — applies across both of Epic 1.8's stories, including this one:

- A way for fully automated, scheduled processes (rather than a signed-in user's action) to call the service — deferred until the first such process (the automated payment run) needs it, in a later phase (client `client_credentials` support moves to Phase 6).
- An admin screen for sending a test email by hand — this phase's proof is a hands-on check with a testing tool during integration testing; admin operations otherwise go through the database team's standard operational procedures.
- A screen for browsing the sent-email history — the same testing tool covers this need for now.

Specific to this story: the "send an email" endpoint itself, its role-based authorisation, its retry loop, and the delivery-history lookup endpoint are Story 1.8.2, not this one — this story only stands up the service, the table, and the email connection.
