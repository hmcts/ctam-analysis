# Story 0.0.3: The natural-key mismatch is discovered and recorded as gap G8.7

Status: ready-for-dev

## Story

As the **person responsible for how CTAM identifies judges and tribunal members**,
I want the practice copy's confirmed person-record shape compared against what the programme had assumed the unique identifier field would be, with any mismatch clearly written down and flagged in the sync team's own code,
so that a structural surprise in the real data source becomes a tracked decision for the team to make, rather than something discovered midway through building the real integration — and whoever eventually resolves it can find every affected spot easily, instead of hunting for it.

## Acceptance Criteria

1. Given the practice copy's person-record shape is now confirmed, when the engineer compares it against the identifier field the programme had assumed would be used, then the mismatch is written down clearly as a tracked, open item (no changes to the actual database design are made here — that's a separate decision).
2. The sync's own code is written against the two fields the real system actually returns, with an obvious, searchable marker left wherever the old assumption still applies, so the eventual fix is a small, well-contained change rather than an open-ended hunt.

## Tasks / Subtasks

- [ ] Task 1 — Confirm and record the mismatch (AC: 1)
  - [ ] Write the failing test asserting the mock's person-record DTO (confirmed in Stories 0.0.1/0.0.2) exposes `per_id` (numeric id) and `personal_code` (10-digit string) and has **no** `personnel_number` field; run; capture the assertion failure showing the missing field (R2, T1)
  - [ ] This assertion is expected to stay red only long enough to prove the mock's shape is what the real Swagger export/example payloads say — once the mock's DTO reflects the real shape, the test documents the mismatch permanently rather than chasing a fix
  - [ ] Write the discovery record: an ADR at `docs/decisions/ADR-00N-joh-natural-key-mismatch.md` (per `_arch/architecture/repo-structure.md`'s `docs/decisions/` convention) stating plainly that `jo_people.personnel_number` — the name CTAM's architecture is built around — does not exist in the real API, which instead returns `per_id` and `personal_code`; which of the two (or a composite) is the stable natural key is explicitly **not decided** by this ADR
  - [ ] Cross-reference the ADR to the control-plane repo's tracked item for this discovery — `ctam-analysis`'s `_bmad-output/planning-artifacts/architecture/gaps.md`, gap **G8.7** — and note in the ADR that G8.7 is not yet reflected in this repo's own `_arch` pin (`bus_version`) at the time of writing, so the ADR is this repo's authoritative record until the bus republishes it
- [ ] Task 2 — Write the sync's own code against the real fields, with a searchable marker (AC: 2)
  - [ ] Write the failing test: the sync's person-mapping code (client/DTO layer for the eLinks person record) maps `perId` and `personalCode` from the mock's response, with no field named or aliased `personnelNumber`; run; capture red
  - [ ] Minimum mapping implementation to pass; re-run
  - [ ] Everywhere the codebase still has to reach for CTAM's assumed identifier name (e.g. at the seam where this maps onto `ctam_joh_identities.personnel_number` per `_arch/architecture/data-tables.md`), mark it with a single, grep-able, named constant or annotation that cites the gap — e.g. a `KNOWN_GAP_G8_7` constant or an `@OpenArchitecturalDecision("G8.7")` marker on the seam — **not** a bare `TODO`/`FIXME` comment, which the leftovers scan forbids and which would misrepresent this as unfinished work rather than a recorded, deliberate open decision

## Dev Notes

### Context distilled from the bus

- [Source: `_arch/architecture/data-tables.md#tier-a--joh-elinks-upstream-sourced--15-tables`] — `jo_people`'s `personnel_number` is documented as "the **upstream natural key** and the link target for `ctam_joh_identities`." [Source: `_arch/architecture/data-tables.md#ctam-owned-joh-identity--1-table`] — `ctam_joh_identities` is described as carrying `personnel_number` (unique — the link to `jo_people`) and being "minted eagerly during the nightly eLinks sync." Both statements are exactly the assumption this story's AC-1 tests against the real mock and finds does not hold.
- [Source: `_arch/architecture/functional-requirements-coverage.md#identity--authorisation-fr1fr5`] — FR1 states the JOH identity-resolution chain as "`jo_people` → `personnel_number` → `ctam_joh_identities`." This is the FR this story's discovery is load-bearing against — hence `frs: [FR1]` in this packet's frontmatter — though resolving FR1's chain (choosing `per_id` vs. `personal_code`) is explicitly **not** this story's job (AC-1: "no changes to the actual database design are made here").
- [Source: `_arch/architecture/gaps.md#g8-1`] — at this packet's `bus_version` (`arch-v1.1`), the bus's own gaps register still assumes `personnel_number` is the natural key and does not yet carry the discovery this story makes. **Important for whoever executes this story**: the fuller, already-written-up version of this exact discovery exists as gap **G8.7** in the control-plane repo (`ctam-analysis`, not `ctam-architecture`) — `_bmad-output/planning-artifacts/architecture/gaps.md`, dated 2026-08-20 — but G8.7 has not yet been republished to the `_arch` bus at this pin. Do not cite `_arch/architecture/gaps.md#g8-7` as if it exists at `arch-v1.1` — it does not. This story's own ADR (Task 1) is what makes the discovery durable *inside this repo* independent of when the bus catches up.
- The real field names (`per_id`, `personal_code`) are not documented anywhere in `_arch` — they come from the real Swagger export and example payloads Stories 0.0.1/0.0.2 built the mock from. If those source materials are not attached to this packet when it is really dispatched, that is a stop (R5) before Task 1 can even start.

### Rules that apply

- [`_arch/agent-rules/00-core.md#r5`] This entire story is a worked example of R5: an upstream field's real meaning turned out not to match the assumption, and the rule is to write it down and stop — not to unilaterally pick `per_id` or `personal_code` and move on. AC-1 says so explicitly.
- [`_arch/agent-rules/00-core.md#r8`] "No unfinished work ships" governs why the Task 2 marker must **not** be a `TODO`/`FIXME` — the leftovers scan treats those as unfinished work, and this discovery is finished, recorded work with an open *decision*, which is a different thing. Use a named constant/annotation that reads as intentional and searchable, not as a stub.
- [`_arch/agent-rules/10-tdd.md#t4`] Treat the mismatch the way a bug-reproduction test is treated: the failing test in Task 1 is the reproduction; it stays in the suite afterwards (renamed to assert the now-confirmed real shape) as the permanent record that the mismatch was checked for, not silently fixed forward.
- [`_arch/agent-rules/40-data-and-liquibase.md#p4`] This story must not alter any table `ctam-reference-data` owns, including `ctam_joh_identities` — no changeset, no column rename. The rename gap-resolution path belongs to a later, separately-approved piece of work.
- [`_arch/agent-rules/50-security-and-logging.md#s1`] Neither `per_id` nor `personal_code` should appear in any log line the sync code adds here — both are person-identifying and fall under the "identifiers" entry in the forbidden-to-log list, exactly like `personnel_number` would have.
