# Story 0.1.1: A provisional MRD workbook shape is proposed and documented

Status: ready-for-dev

## Story

As the **engineer building the MRD data-loading work** (and everyone who maintains it afterwards),
I want a specific, concrete proposal for what the MRD workbook contains and how it's laid out, clearly labelled as an assumption rather than a confirmed fact,
so that there is something concrete to design and test against today, instead of an open-ended unknown that blocks progress indefinitely.

## Acceptance Criteria

1. Given the database table for JOH Specialisms already exists, when the engineer proposes a workbook shape for it, then the proposal specifies a single sheet with one row per specialism per judge, and names every column needed to populate that table — a judge reference, a jurisdiction, a specialism code and description, and an effective date — and the proposal is written down alongside a clear statement that it is a working assumption, not a confirmed fact, and where the open question is being tracked.
2. Given the proposed shape, when it's reviewed against what the programme already knows it needs from MRD, then every column in the proposal traces back to something the programme has already documented needing, rather than being invented from nothing.

## Tasks / Subtasks

- [ ] Task 1 — Encode the proposed shape as a concrete, testable schema descriptor (AC: 1)
  - [ ] Write the failing test asserting `MrdSpecialismWorkbookSchema` exposes exactly the sheet name and the five expected columns, in order (`judgeReferenceNumber`, `jurisdiction`, `specialismCode`, `specialismDescription`, `effectiveFrom`); run it, capture the assertion failure (R2, T1)
  - [ ] Add the minimum `MrdSpecialismWorkbookSchema` descriptor under `src/test/java/uk/gov/hmcts/ctam/referencedata/support/` to make it pass; re-run, capture the pass (T1). This is test-support code, not `src/main/**` — the practice workbook and everything describing its shape lives entirely inside the test setup, per the epic's "Hosting" note — so R2's red-before-green discipline is followed by choice (good practice, T1) rather than by R2's own literal scope
  - [ ] Write the proposal narrative into the descriptor's Javadoc: what each column means, and an explicit statement that this is a working assumption, not a confirmed fact, citing where the open question is tracked (`_arch/architecture/gaps.md#g8--upstream-reference-data-integration`, gap G8.1's 2026-08-21 update)
- [ ] Task 2 — Trace every proposed column back to a documented programme need (AC: 2)
  - [ ] For each column, cite the specific documented need it satisfies and record the trace in the same Javadoc, alongside the column it supports: `judgeReferenceNumber` and `jurisdiction` trace to the `mrd_specialisms` row's stated purpose and consumers (`_arch/architecture/data-tables.md#tier-a--mrd-upstream-sourced--1-table`); `specialismCode`/`specialismDescription` trace to "JOH Specialisations — supplementary attributes not present in JOH eLinks" in that same row; `effectiveFrom` traces to the tier-(a) upstream-sourced pattern requiring an upstream-effective date rather than a CTAM-assigned one (`_arch/architecture/conventions.md#naming-patterns` — audit columns are separate from business-effective dates)
  - [ ] This is a traceability review, not a runtime behaviour — there is no test to write for it; record the completed trace as a checklist item in the Dev Agent Record, not as a code assertion (per R4: cite or ask)

## Dev Notes

### Context distilled from the bus

- The `mrd_specialisms` table this proposal is checked against already exists by the time this story runs, created by Story 1.3.1's Liquibase changeset `db/changelog/002-init-mrd-tables.sql`, owned by `ctam_reference_data` with the same write protection as the `jo_*` tables (`_arch/architecture/conventions.md#naming-patterns`: "`jo_` / `mrd_` — upstream-sourced tier-(a) tables... Read-only in CTAM; written only by the ingestion mechanisms").
- `_arch/architecture/data-tables.md#tier-a--mrd-upstream-sourced--1-table`: `mrd_specialisms` — "JOH Specialisations — supplementary attributes not present in JOH eLinks. Further `mrd_*` tables are added as MRD entities enter scope." Key consumers: JOH profile views, Vacancy matching. This is the only documented "what MRD needs to supply" content the proposal can trace against — there is no richer upstream spec.
- `_arch/architecture/gaps.md#g8--upstream-reference-data-integration` (G8.1, updated 2026-08-21): "no real reference example of the MRD workbook exists, unlike the eLinks side. Epic 0.1 (`mrd-reference-data-mock`) proposes a reasoned, explicitly-provisional workbook shape... the proposal is tracked as an open assumption, not treated as resolving this gap." This story's proposal is exactly that open assumption — it must say so, not imply confirmation.
- `_arch/architecture/conventions.md#naming-patterns`: `personnel_number` is the upstream link to `jo_people`, stored only on `ctam_joh_identities`, and is never a domain FK. Whichever field this proposal calls "judge reference number" is a **workbook-column name**, not a claim about the domain FK shape — it must not be conflated with `personnel_number` or `joh_id` in Java code introduced by this story.
