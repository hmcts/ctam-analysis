# Story 1.5.1: Tier-(b) CTAM-owned reference tables, seed data, and the DBA maintenance runbook

Status: ready-for-dev

## Story

As a **platform engineer** (and the database administrators who look after reference data during MVP),
I want the 15 CTAM-owned reference tables created, pre-populated with data, and covered by a written maintenance runbook,
so that **reference data CTAM owns outright — because it doesn't come from any upstream system, like regions, offices, and calendar boundaries — is available to every service and can be kept up to date safely, without ever being overwritten by the upstream data sync**.

## Acceptance Criteria

1. **Given** `ctam-reference-data` has already been set up and carries the judge/tribunal-member tables from an earlier piece of work, **when** the engineer adds the database change script that creates the CTAM-owned tables, **then** the 15 tables exist with the schemas documented in the architecture's data-tables reference: `ctam_regions`, `ctam_offices`, `ctam_calendar_periods`, plus the 12 operational vocabulary tables (`ctam_joh_types`, `ctam_work_types`, `ctam_court_types`, `ctam_ticket_types`, `ctam_session_types`, `ctam_absence_types`, `ctam_working_pattern_types`, `ctam_booking_statuses`, `ctam_sitting_outcomes`, `ctam_joh_fee_entitlements`, `ctam_payment_lifecycle_statuses`, `ctam_reconciliation_statuses`); **and** the `ctam_reference_data` database role owns these tables; **and** every current and planned service has been granted read-only (SELECT) access to them; **and** an automated check confirms both that the tables are owned correctly and that the upstream data-sync code path cannot write to any of these tables, keeping CTAM-owned data and synced data cleanly separated; **and** the three tables that currently overlap with the JOH data source (`ctam_joh_types`, `ctam_court_types`, `ctam_ticket_types`) carry a note in their schema explaining that each may be retired in favour of its JOH-sourced equivalent, once the JOH data source's contract is fully confirmed.

2. **Given** the engineer adds the database change script that seeds the CTAM-owned data, **when** that change script runs, **then** `ctam_regions`, `ctam_offices`, `ctam_calendar_periods`, and all 12 vocabulary tables are populated with the documented, agreed values, matching the architecture's data-tables reference; **and** the seeded values include the entries expected to matter for the Employment Tribunals wave-1 rollout (for example, the session and work types used in Employment Tribunal sittings), flagged as needing confirmation once the detailed Employment Tribunals as-is analysis is complete; **and** development and CI environments get exactly the same seed data through the same standard change-script mechanism — there is no separate way of seeding this data for testing.

3. **Given** the DBA maintenance runbook is written and published in the architecture repository, **when** a change to the CTAM-owned data is needed during MVP (for example, adding a new office or a new vocabulary value), **then** the runbook documents who needs to request the change and why, the SQL pattern to use for that table, how to verify the change worked, and how to undo it if needed; **and** the runbook states clearly that the judge and tribunal-member data is never hand-edited inside CTAM — corrections happen at the original source and arrive automatically on the next sync; **and** the runbook is linked from the service's own README.

## Dev Notes

### Context distilled from the bus

- Table ownership and the tier-(b) list are fixed by [`_arch/architecture/data-tables.md`](../../../../../../ctam-architecture/architecture/data-tables.md): `ctam_regions`, `ctam_offices`, `ctam_calendar_periods` are "Domain"; the 12 vocabulary tables are "Vocabulary". `ctam_joh_types`, `ctam_court_types`, `ctam_ticket_types` are each marked **"Upstream-overlap candidate"** against a named `jo_*` equivalent, tracked as gap **G8.2** — "resolved alongside G8.1 when the eLinks contract is confirmed; each retirement is a Liquibase changeset + `data-tables.md` update" (`_arch/architecture/gaps.md` → G8.2). This story only adds the note; it does not retire anything.
- Ownership tiers: `_arch/architecture/data-tables.md` — tier (b) "CTAM-owned (everything else)" is written by "the owning service; DBAs via SQL per runbook in MVP", with cross-service access "Yes (per tier-(b) rules) — within CTAM". Tier (b) tables "never overwritten by upstream sync."
- Naming: `_arch/architecture/conventions.md` → *Naming Patterns* — `ctam_` prefix, entity-plural, `snake_case`, `uuid` PK named `id`, audit columns `created_at`/`updated_at timestamptz NOT NULL`.
- Cross-service grant maintenance is gap **G6.4**: "grants codified in the table-owning service's Liquibase changelogs; PR template includes a 'grants checklist'; ArchUnit-style fitness function in CI verifies declared grants match actual code-level cross-service table access" (`_arch/architecture/gaps.md` → G6.4). Task 3/4 implement exactly this.
- Runbook precedent: `_arch/architecture/data-tables.md` and `_arch/architecture.md` both describe tier-(b) maintenance as "DBAs via direct SQL per operational runbooks in MVP; admin UI post-MVP" (D10). The `ctam-architecture` repo's own `runbooks/` folder currently holds `incident-response.md` and `per-region-rollout-playbook.md` (`_arch/architecture/repo-structure.md`); this story adds the DBA reference-data maintenance runbook alongside them.

### Rules that apply

- [`_arch/agent-rules/40-data-and-liquibase.md`](../../../../../../ctam-architecture/agent-rules/40-data-and-liquibase.md) — P1 (Liquibase DDL, and Liquibase *is* the sanctioned path for CTAM-owned static-vocabulary seed rows — never an ingestion path), P2 (applied changesets are immutable — fix forward only), P3 (one logical change per changeset, with a rollback), P4 (you may only change tables you own — these 15 are `ctam-reference-data`'s own, so this is in-bounds), P6 (every migration proved against real PostgreSQL via Testcontainers; H2 prohibited), P16 (audit columns populated by the application from an injected `Clock`, never a trigger or default — not directly exercised by seed rows, but the table shape must support it).
- [`_arch/agent-rules/10-tdd.md`](../../../../../../ctam-architecture/agent-rules/10-tdd.md) — T8 (every schema change gets an integration test run from an empty database).
- [`_arch/agent-rules/00-core.md`](../../../../../../ctam-architecture/agent-rules/00-core.md) — R2 (red before green, with evidence — applies to Tasks 1–5; Task 6 is documentation, not `src/main/**`), R6 (no unsanctioned surface — the 15 tables and their columns are exactly what's cited above, nothing more), R9 (limits are the design speaking — see `20-modularity.md` if any changeset grows unwieldy).

### Project Structure Notes

- Changesets land at `src/main/resources/db/changelog/NNN-name.sql`, registered in `db.changelog-master.yaml`, per `_arch/architecture/conventions.md` → *Structure Patterns* and `_arch/architecture/repo-structure.md`'s per-service tree.
- The DBA maintenance runbook is a **cross-repo** deliverable: the runbook document itself is published under `ctam-architecture/runbooks/` (sibling to `incident-response.md` and `per-region-rollout-playbook.md`, per `_arch/architecture/repo-structure.md`), which is outside this story's own repo and this story's write scope. This story's diff in `ctam-reference-data` is limited to the link in this repo's `README.md`. Landing the runbook file itself requires a separate change against `ctam-architecture` — flagged here rather than assumed away.

### Out of scope / boundaries

- A maintenance screen for RSU staff to manage this data — planned for the admin UI (`ctam-admin-ui`) after MVP (D10).
- Any API endpoint for writing to the CTAM-owned data — Story 1.5.2 is read-only; there is no write surface on this data through any API in any phase covered here.
- Retiring `ctam_joh_types`, `ctam_court_types`, or `ctam_ticket_types` in favour of their JOH-sourced equivalents — that happens later, once G8.1/G8.2 resolve, as its own Liquibase changeset.
- Loading the actual JOH eLinks data sync (Story 1.2.1) — this story only creates and seeds CTAM-owned tables; it does not touch the upstream-sourced `jo_*` tables.
