# Story 1.2.1: JOH reference data flows into CTAM nightly from the JOH eLinks feed

Status: ready-for-dev

## Story

As **the CTAM Pathfinder platform**, and everyone downstream who relies on judicial-holder data being accurate,
I want **a nightly automated process that pulls judicial-holder data from the JOH eLinks feed and refreshes CTAM's own copy of it**,
so that **the people table is always populated and current, jurisdiction information is available, and judicial-holder reference data is authoritative within CTAM — without needing to migrate any data from legacy systems**.

## Acceptance Criteria

1. **Given** the database tables for judicial-holder data and the run-status logging table already exist from the earlier schema work (Story 1.1.2),
   **When** the engineer builds the nightly sync as an automated task running inside the existing service, needing no separate deployment or service account,
   **Then** it runs on its nightly schedule and pulls all 15 categories of data from the JOH eLinks feed, using a credential held securely in Azure Key Vault,
   **And** it fully refreshes and updates each table, matching records on the source system's own reference number for each one (the field the epic names as `personnel_number`, for people — see Dev Notes → Recorded deviations for why this needs care), and creates a stable CTAM-assigned identifier (in the `ctam_joh_identities` table) for any person who doesn't already have one,
   **And** any record that has disappeared from the source system is marked inactive rather than deleted, so nothing else in the database that refers to it is ever broken,
   **And** each run is recorded in the `ctam_sync_status` table with where it came from, when it started and finished, its outcome, how many rows of each type it processed, and any error details,
   **And** the process can also be triggered manually by the operations team — for example through an admin endpoint or a one-off job — for an extra, out-of-cycle refresh.

2. **Given** the JOH eLinks feed is unreachable, or sends back data in an unexpected shape, partway through a run,
   **When** the sync fails,
   **Then** the previously loaded data is left completely intact — each category of data is loaded as a single all-or-nothing unit, so nothing is ever left half-written,
   **And** the failure is recorded in the run log and reported through the platform's standard structured logging, tagged with a correlation ID so operations staff can trace exactly what happened,
   **And** the reference data is never more than one sync cycle — one night — out of date.

3. **Given** the sync has run successfully at least once in a development environment,
   **When** the sign-in service looks up a judicial office holder by a seeded email address,
   **Then** the lookup successfully resolves through the people table to that person's reference number, and from there to their CTAM-assigned identifier,
   **And** development and test environments can run against realistic seeded sample data when a live connection to the JOH eLinks feed isn't available, with the sync itself checked automatically in continuous integration against a realistic stand-in for the real feed.

4. **Given** the exact shape of the JOH eLinks feed has not yet been formally confirmed,
   **When** that confirmation becomes available,
   **Then** the way this process maps incoming data onto CTAM's own tables is checked against it — making sure every field CTAM needs has somewhere to go, the way each record is uniquely identified still holds up, and the timing of the real feed is workable,
   **And** if anything about the real feed's data doesn't fit what was assumed, that is raised as a formal design question rather than quietly worked around — this check is an explicit, tracked step in planning the work, not an afterthought.

## Dev Notes

### Context distilled from the bus

- **Tier-(a) tables are read-only outside this service's ingestion path.** `jo_*` tables are the source-system-prefixed tier, "refreshed nightly by the in-process scheduled sync. Upserts key on the upstream natural key; rows absent upstream are marked inactive, never hard-deleted (protects FKs from domain tables)." [Source: `_arch/architecture/data-tables.md` — tier-(a) intro, line ~46]
- **`jo_people` and its natural key:** "`jo_people` | JOH person records; `personnel_number` is the upstream natural key and the link target for `ctam_joh_identities`. CTAM's canonical JOH identifier is the UUID in `ctam_joh_identities`, resolved at sign-in from the IdP email." [Source: `_arch/architecture/data-tables.md`, `jo_people` row] — **but read this alongside G8.7 below before writing the mapping code.**
- **`ctam_joh_identities` is mint-only:** "Written by the eLinks sync **mint-only** (a new `personnel_number` gets a new UUID; existing mappings are never changed or deleted) and SELECT-granted to every domain service. This insulates CTAM domain data from upstream `jo_people` churn." Every domain table references the JOH by `joh_id`, never by the upstream natural key. [Source: `_arch/architecture/data-tables.md`, `ctam_joh_identities` section]
- **`ctam_sync_status` is this story's own run-log table:** "Ingestion run log — per-run source, started/finished, outcome, row counts, error detail. CTAM-internal tracking entity with no upstream source. Feeds the wave-gate 'reference data current' check and ops triage." [Source: `_arch/architecture/data-tables.md`, `ctam_sync_status` row]
- **Scheduling is an implementation choice, both acceptable at MVP:** "implementation choice between Spring `@Scheduled` (in-process; runs inside the same JVM as the synchronous service API) and a Kubernetes CronJob (separate pod; scales independently). Either is acceptable at MVP." [Source: `_arch/architecture/conventions.md` → *Communication Patterns*, "Service-principal authentication (for batch / scheduled components)"] The epic's own "no separate deployment or service account" framing points to the in-process `@Scheduled` option, but either satisfies the architecture.
- **The manual admin-trigger endpoint is a normal authenticated endpoint**, not a special case: it goes through the same `JWTFilter` → `AuthDetails` path as every other endpoint (S9), and states its required permission explicitly (S11).
- **What the Epic 0.0 mock actually provides for this story's CI tests** (do not assume more than this): a local, CI-only reference mock of the real JOH eLinks People API v5, built from the real Swagger export and seeded at real production scale (`locations`: 2000, `base_locations`: 1462, `appointment_titles`: 194, `judiciary_roles`: 164, `tickets`: 159, `ticket_categories`: 54, plus the small fixed vocabularies). It confirms the endpoint set, bearer-token auth, the pagination envelope, and change-feed semantics (`/people?updated_since=`, `/leavers?left_since=`, `/deleted?deleted_since=`) — this is the "realistic stand-in for the real feed" AC-3 requires this sync be CI-tested against. It does **not** confirm the real feed itself beyond what the Swagger export captured, and it explicitly does not resolve which field CTAM should use as the person natural key (see G8.7 immediately below) — that decision is out of scope for the mock and for this story. [Source: `_arch/architecture/gaps.md` → G8.7; epic `_bmad-output/planning-artifacts/epics/phase-0/epic-0.0-joh-elinks-api-contract-mock.md`]

### Project Structure Notes

Per the generic per-service layout [Source: `_arch/architecture/conventions.md` → *Structure Patterns*], this story's code lands as:

- `client/` — the JOH eLinks HTTP client (lookup-data endpoints, `/people`, `/leavers`, `/deleted`), carrying the Key Vault-resolved bearer token
- `service/` — the sync orchestration (per-category load, upsert, deactivation, mint-only identity creation, run-status recording) and the `@Scheduled` trigger
- `repository/` — Spring Data JPA repositories for the 15 `jo_*` entities, `ctam_joh_identities`, and `ctam_sync_status`
- `domain/` — the corresponding read-only-mapped `jo_*` entities (P5 — map read-only even though this service is the writer of record via SQL, keep JPA writes going through the sync's own upsert path, not generic `save()` calls that could be reused elsewhere) plus `CtamJohIdentity` and `CtamSyncStatus`
- `controller/` — the manual-trigger admin endpoint
- `config/` — Key Vault client wiring, `@Scheduled` cron config, the eLinks `RestClient` bean

**Note:** `conventions.md`'s documented package list (`controller/service/repository/domain/dto/client/config/error/exception`) has no dedicated `ingestion/`/`scheduler/`/`batch/` package for a nightly sync. This packet places the trigger and orchestration inside `service/`, consistent with the existing package set, rather than introducing a new top-level package — flagged here per R6 so a reviewer can see the choice was made deliberately, not by default. If the dev agent judges the sync large enough to warrant its own sub-package, that is a design decision to record here, not one to make silently.

No Liquibase changeset belongs to this story — the 15 `jo_*` tables, `ctam_joh_identities`, and `ctam_sync_status` are Story 1.1.2's surface (P4). If any column this sync needs turns out to be missing from that schema, that is an R5 stop against Story 1.1.2, not something to patch from here.

### Out of scope / boundaries

- Bringing in the separate weekly MRD data feed — that's Epic 1.3, Story 1.3.1.
- The database tables and their write-protection rules themselves — designed and locked down in Epic 1.1, Story 1.1.2; this story only fills them with data.
- The read-only lookup service that will expose this data to other services — Epic 1.5, a separate, later piece of work.
- Deciding which field (`per_id`, `personal_code`, or a composite) becomes CTAM's permanent upstream natural key — that is a standing open architectural decision (gaps.md G8.7), not made by this story. This story's job is to build the sync in a way that survives that decision being made later (see Recorded deviations, below).

### Recorded deviations

- **DEV-1.2.1-G8.7 — the epic's AC-1 names `personnel_number` as the field records are matched on; the confirmed contract does not have that field.** Rule/text affected: Epic 1.2 Story 1.2.1, AC-1 ("matching records on the source system's own reference number for each one (the `personnel_number` field, for people)"); also `_arch/architecture/data-tables.md`'s `jo_people` and `ctam_joh_identities` entries, and decision D9, which are all written in terms of `personnel_number`. Authority for the deviation: `_arch/architecture/gaps.md` → **G8.7** (2026-08-20) — the CI-only reference mock, built from the real JOH eLinks Swagger export, shows the real person record has **no `personnel_number` field**; it returns `per_id` (numeric) and `personal_code` (10-digit string) instead. G8.7's own resolution path states: "the sync's own code is written against the two fields the real system actually returns, with an obvious, searchable marker left wherever the old assumption still applies, so the eventual fix is a small, well-contained change rather than an open-ended hunt" — and explicitly notes this is a decision for the team to make, not resolved by the mock or by this story.
  **What this means for this story's code:** map the sync against `per_id`/`personal_code` as the fields the mock (and, per G8.7, the real API) actually returns. Everywhere the code, tests, DTOs, or comments would otherwise have named `personnel_number` on the *incoming eLinks payload* (as opposed to the already-existing `jo_people.personnel_number` / `ctam_joh_identities.personnel_number` **columns**, which are Story 1.1.2's schema and out of scope to rename here), leave an obvious, greppable marker — e.g. a `// G8.7:` comment at the mapping point — so the eventual rename sweep (once the team decides which field is the permanent natural key) is mechanical. Do not silently pick one of `per_id`/`personal_code` and treat it as settled; do not rename the schema columns from this story (that is Story 1.1.2's / a future migration's surface, not this ingestion story's).
  Approved by: recorded in `gaps.md` itself as the sanctioned way to proceed pending the architectural decision — this is not a deviation this packet is inventing, it is following the gap's own written resolution path. No further human sign-off was sought for this draft packet (see the DRAFT banner); a real dispatch of this story should have a human confirm this reading of G8.7 before work starts.
