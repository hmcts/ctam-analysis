# Story 1.1.2: The 15 outside-sourced tables exist, with write access locked to this service alone

Status: ready-for-dev

## Story

As **the CTAM Pathfinder platform** (and every future feature that reads judge and tribunal-member data),
I want the 15 database tables that hold judge, appointment, role, location, and ticket data sourced from outside CTAM, plus the run-log table for data-sync jobs, created through this service's own versioned migration scripts, with write access locked down so that only `ctam-reference-data` can ever change them,
so that **the judge and tribunal-member data these tables will eventually hold exists with the right structure and the right protection before the nightly JOH data sync starts loading real data into it**.

## Acceptance Criteria

1. **Given** `ctam-reference-data` has already been scaffolded as described in Story 1.1.1, **when** the engineer adds a new database-migration changeset (formatted SQL, included from the master changelog), **then** all 15 outside-sourced (`jo_*`) tables exist with the structure documented in `_arch/architecture/data-tables.md`: the people table (`jo_people`), the appointments table (`jo_appointments`), the judiciary role-assignment table (`jo_judiciary_role_assignments`), the authorisations-with-dates table (`jo_authorisations_with_dates`), plus the appointment-titles, base-locations, contract-types, genders, judiciary-roles, jurisdictions, locations, location-types, tickets, ticket-categories, and ticket-category-types tables (`jo_appointment_titles`, `jo_base_locations`, `jo_contract_types`, `jo_genders`, `jo_judiciary_roles`, `jo_jurisdictions`, `jo_locations`, `jo_location_types`, `jo_tickets`, `jo_ticket_categories`, `jo_ticket_category_types`).
2. **And** the `ctam_sync_status` run-log table for tracking data-sync jobs also exists, in the same migration.
3. **And** `jo_people.personnel_number` is treated only as the source system's own natural identifier and the link back to the source system — it is never CTAM's internal identifier for a person; CTAM's own stable, CTAM-generated unique ID per person is bound in a separate identities table, which every other part of the platform actually refers to (that separate identities table is not created by this story — see *Out of scope*).
4. **And** `jo_jurisdictions` preserves the parent-child hierarchy the source system uses, either carried over from the upstream data on load or built in as data is first loaded.
5. **And** the `ctam_reference_data` database role owns all 16 tables created by this story (the 15 `jo_*` tables plus `ctam_sync_status`), and no other database role is ever granted permission to `INSERT` or `UPDATE` rows in any of them — the enforced single-writer rule for this outside-sourced data.
6. **And** read-only (`SELECT`) access is granted to the authorisation service's database role (for identity look-ups) and to placeholder roles reserved for future consuming services.
7. **And** an automated check runs in the CI pipeline that verifies the write-protection rule in AC-5 actually holds, so it can never silently regress.

## Dev Notes

### Context distilled from the bus

- The exact 15 `jo_*` tables and their purposes are enumerated in `_arch/architecture/data-tables.md#tier-a--joh-elinks-upstream-sourced--15-tables`: `jo_people`, `jo_appointments`, `jo_judiciary_role_assignments`, `jo_authorisations_with_dates`, `jo_appointment_titles`, `jo_base_locations`, `jo_contract_types`, `jo_genders`, `jo_judiciary_roles`, `jo_jurisdictions`, `jo_locations`, `jo_location_types`, `jo_tickets`, `jo_ticket_categories`, `jo_ticket_category_types` — this matches the epic's own list exactly; no discrepancy to flag. `ctam_sync_status` is documented separately under `_arch/architecture/data-tables.md#ctam-internal-sync-tracking--1-table` as "Ingestion run log — per-run source, started/finished, outcome, row counts, error detail. CTAM-internal tracking entity with no upstream source."
- Tier (a) tables are upserted on the upstream natural key by the ingestion mechanism, and rows absent upstream are marked inactive, never hard-deleted (protects FKs from domain tables) — this story only creates the shape; the ingestion behaviour itself is Epic 1.2 [Source: `_arch/architecture/data-tables.md#reference-data-service-ctam-reference-data--33-tables`].
- `jo_people.personnel_number` is the upstream natural key and the link target for the separate `ctam_joh_identities` table, which holds CTAM's own canonical JOH UUID; that identities table is minted **eagerly during the nightly eLinks sync** (Epic 1.2), not by this story [Source: `_arch/architecture/data-tables.md#ctam-owned-joh-identity--1-table`]. This story's AC-3 is a structural constraint on `jo_people` (a natural-key column, not an overloaded identifier) — it does not require creating `ctam_joh_identities` here.
- The two-ownership-tier model (FR6/FR7): tier (a) (`jo_*`, `mrd_*`) is written only by the ingestion mechanisms under the `ctam_reference_data` role and is **never** hand-editable in CTAM at any phase; corrections happen at the source system and arrive on the next sync [Source: `_arch/architecture/data-tables.md#the-two-ownership-tiers-fr6fr7`].
- The fitness function required by AC-7 is the same class of check named in the bus: every table created by Liquibase DDL must appear in `data-tables.md` with the matching owning service, and DB role grants must align — including the tier-(a) rule that only `ctam_reference_data` holds `INSERT`/`UPDATE` on `jo_*`/`mrd_*` tables [Source: `_arch/architecture/data-tables.md#inventory-totals` (fitness-function note) and `_arch/architecture/conventions.md#enforcement-guidelines`].

### Rules that apply

- `_arch/agent-rules/40-data-and-liquibase.md#p1` (Liquibase DDL only, formatted-SQL changeset registered in the master changelog — no Flyway), `#p2` (once this changeset runs anywhere it is immutable — fix forward with a new changeset, never edit it), `#p3` (one logical change per changeset, with a stated rollback), `#p4` (this service may only create/alter tables it owns — all 16 tables here are owned by `ctam_reference_data`; cross-service `GRANT`s for the authorisation/placeholder roles belong in *this*, the owning service's, changelog), `#p5` (`jo_*` tables are read-only from every service but this one — no writable JPA entity may ever be mapped to them), `#p6` (every migration proved against real PostgreSQL via Testcontainers — H2 prohibited), `#p16` (every table gets `created_at`/`updated_at timestamptz NOT NULL`, set by the application from an injected `Clock`, not a DB trigger or default).
- `_arch/agent-rules/10-tdd.md#t8` (every schema change gets an `*IT`) and `#t16` (the JaCoCo/PIT floor applies to `service`/`domain` packages only — Liquibase changelogs themselves are excluded from all three gates, but any read-only JPA entity/repository added for the `*IT`s to exercise is not).
- `_arch/agent-rules/20-modularity.md#m11` (if read-only JPA entities are added for `jo_*` in this story's own test/verification path, `domain` stays pure) and `#m20` (no `LocalDate.now()`/`Instant.now()` — audit columns are set from an injected `Clock`, consistent with P16).
- `_arch/agent-rules/00-core.md#r6` (no unsanctioned surface area — exactly the 16 tables named in the ACs; no speculative column, index, or table beyond what `data-tables.md` documents) and `#r14` (no uninvited work — do not also create `ctam_joh_identities` or any tier-(b) table here; that is explicitly other work).

### Project Structure Notes

Per `_arch/architecture/conventions.md#structure-patterns`, the changeset lands at:

```
ctam-reference-data/
├── src/main/resources/db/changelog/
│   ├── db.changelog-master.yaml         (updated to include the new changeset)
│   ├── 001-jo-reference-tables.sql      (formatted SQL, the 15 jo_* tables + grants)
│   └── 002-ctam-sync-status.sql         (formatted SQL, the run-log table + grants)
├── src/test/java/uk/gov/hmcts/ctam/referencedata/
│   └── db/                              (Testcontainers *IT for schema shape + grants)
```

Table/column/index naming follows `_arch/architecture/conventions.md#naming-patterns`: `snake_case` tables and columns, `uuid id` primary keys, foreign keys as `{referenced_entity_singular}_id`, indexes `idx_{table}_{columns}`, unique constraints `uq_{table}_{columns}`. No `controller/`, `service/`, or `dto/` changes are expected this story — this is a pure persistence-layer story (R6); any JPA entity added purely to support the `*IT`s stays in `domain/` and is mapped read-only per P5.

### Out of scope / boundaries

- The nightly JOH data sync that will actually populate these tables with real data.
- The weekly MRD data sync, and the separate `mrd_*` tables it owns.
- CTAM's own reference tables (regions, offices, controlled vocabularies) — later work.
- The read-only API that will eventually expose this data to other services.
- Creating `ctam_joh_identities` (the separate CTAM-generated identity table referenced structurally in AC-3) — that table is minted by the nightly eLinks sync in Epic 1.2, not by this story.
