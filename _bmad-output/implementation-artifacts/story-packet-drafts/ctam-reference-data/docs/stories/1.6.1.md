# Story 1.6.1: JOH Specialisations are made available through the Reference Data read-only API

Status: ready-for-dev

## Story

As an **API consumer** — the CTAM front end, and other downstream services in later phases that need to know a judge's specialisms, such as Itinerary planning —
I want a read-only, jurisdiction-filtered endpoint over the JOH Specialisations data, added onto the existing Reference Data API,
so that **this information can be looked up through the one API surface these services already use, without needing to discover and integrate with a second API or run a second set of automated checks**.

## Acceptance Criteria

1. Given the JOH Specialisations data already exists and has been loaded, and the Reference Data API's existing read infrastructure — security-token checking, jurisdiction-based filtering, a standard error-response format, and versioned web addresses under `/v1/reference-data/...` — is already in place, when the engineer adds a new endpoint, `GET /v1/reference-data/johs/{johId}/specialisms`, then the endpoint returns a successful response with that judge's list of specialisms, found by tracing from the judge's identity through to their personnel number and on to the specialisms data, and the response is filtered by jurisdiction in exactly the same way as every other endpoint on this API — someone asking about a judge outside their own jurisdiction gets a clear "not allowed" response, not an empty result that pretends the judge doesn't exist, and a judge who genuinely has no specialisms on record gets back a successful response with an empty list, not a "not found" error, and no ability to create, update, or delete specialisms is provided — any attempt to do so is clearly rejected with a "method not allowed" response explaining that corrections happen back at the source system and arrive via the next scheduled data sync.
2. Given the API's technical definition is regenerated, when the engineer publishes the updated version, then the published package moves to its next version (not a new, separate package) with the new endpoint documented alongside everything already there, and the automated linting check that keeps the API definition consistent with the rest of the programme's APIs still passes.
3. Given the existing collection of automated API checks used in continuous integration, when it runs, then it gains a new set of checks for the new endpoint — the successful case, the jurisdiction-filtered rejection, the empty-list case, and the rejected write attempt — sitting alongside the checks already in place for the other reference data this API covers.

## Dev Notes

### Context distilled from the bus

- This story adds **one** `GET` endpoint onto the Reference Data API that Story 1.5.2 already published — the same `JWTFilter`/`AuthDetails` jurisdiction-filtering, RFC 9457 error shape, and `/v1/reference-data/...` versioning it already uses; nothing new is stood up [Source: epic-1.6 "Hosting"; `_bmad-output/planning-artifacts/epics/phase-1/epic-1.5-joh-reference-data-read-api.md` Story 1.5.2].
- `mrd_specialisms` is described as "JOH Specialisations — supplementary attributes not present in JOH eLinks... Further `mrd_*` tables are added as MRD entities enter scope," with key consumers "JOH profile views (FR11), Vacancy matching" [Source: `_arch/architecture/data-tables.md` → "Tier (a) — MRD upstream-sourced"]. Itinerary (named in this story's role/benefit) is not yet listed as a consumer at `bus_version: arch-v1.1` — that is the epic's forward-looking rationale, not yet reflected in the published bus; do not infer it is wired up anywhere today.
- Identity chain for the join: the path variable is the CTAM-assigned JOH UUID — "JOH resources key on the CTAM JOH UUID — `/v1/johs/{johId}`" [Source: `_arch/architecture/conventions.md` → "Naming Patterns"] — resolved via `ctam_joh_identities` to its `personnel_number`, "the unique... link to `jo_people`" [Source: `_arch/architecture/data-tables.md` → "CTAM-owned JOH identity"], which is the key `mrd_specialisms` is keyed against. "Every CTAM domain table references the JOH by `joh_id` → `ctam_joh_identities.id`, never by `personnel_number`" [Source: `_arch/architecture/conventions.md` → "Naming Patterns"] — so `personnel_number` is an internal resolution step inside this service, never itself exposed as the resource identifier.
- `mrd_specialisms` is a tier-(a), source-prefixed table: "Read-only in CTAM; written only by the ingestion mechanisms" [Source: `_arch/architecture/conventions.md` → "Naming Patterns"]. No entity mapped to it may be writable — "No `INSERT`, `UPDATE`, `DELETE`, or DDL against upstream-sourced tables from any service other than `ctam-reference-data`'s ingestion path. No JPA entity mapped to them is writable — map them read-only" [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P5]. This story adds no Liquibase changeset — the table already exists from Story 1.3.1.
- Jurisdiction filtering is the same mechanism Story 1.5.2 built: "every response is automatically filtered to the caller's jurisdiction... using the jurisdiction hierarchy to correctly include or exclude parent and child jurisdictions" [Source: `_bmad-output/planning-artifacts/epics/phase-1/epic-1.5-joh-reference-data-read-api.md` Story 1.5.2 AC], sourced from `AuthDetails`, never a JWT claim directly [Source: `_arch/agent-rules/50-security-and-logging.md` → S9, S10].
- `/v1` is append-only, and adding this endpoint is exactly the case that rule permits without a new major version: "Within a published major version you may... add an endpoint" [Source: `_arch/agent-rules/30-api-contracts.md` → C4]. The published package moves to its next version, same coordinates: `uk.gov.hmcts.ctam:api-ctam-reference-data:{next}` [Source: `_arch/agent-rules/30-api-contracts.md` → C5; `_bmad-output/planning-artifacts/epics/phase-1/epic-1.5-joh-reference-data-read-api.md` Story 1.5.2 AC — package `uk.gov.hmcts.ctam:api-ctam-reference-data:1.0.0`].
- The rejected-write case is the same pattern Story 1.5.2 already established for its own endpoints: "there are no endpoints for creating, changing, or deleting data (`POST`, `PUT`, `PATCH`, `DELETE`) — attempting one is rejected with a `405 Method Not Allowed` response, in the standard 'problem details' error format" [Source: `_bmad-output/planning-artifacts/epics/phase-1/epic-1.5-joh-reference-data-read-api.md` Story 1.5.2 AC]. `conventions.md`'s fixed exception→status table does not enumerate a 405 mapping explicitly — treat this as reusing the existing `@ControllerAdvice` behaviour Story 1.5.2 built, not as inventing a new problem-type category (C8).

### Project Structure Notes

- The new endpoint is added to the existing `ctam-reference-data` controller/service/client layers Story 1.5.2 already established — no new package, no new module (R6/R14). It is a sub-resource of the existing JOH resource, following the pattern already in use: "Sub-resources: `/v1/johs/{johId}/working-patterns`, `/v1/johs/{johId}/tickets`" [Source: `_arch/architecture/conventions.md` → "Naming Patterns"] — this story's path is `/v1/reference-data/johs/{johId}/specialisms`, per the epic's own AC text.
- No Liquibase changeset in this story — `mrd_specialisms` already exists from Story 1.3.1 (`db/changelog/002-init-mrd-tables.sql`) [Source: `_bmad-output/planning-artifacts/epics/phase-1/epic-1.3-mrd-reference-data-etl-process.md`].
- The OpenAPI spec, Pact provider-verification suite, and `postman/ctam-reference-data-phase0.postman_collection.json` are the same artefacts Story 1.5.2 created — this story extends them, it does not create parallel copies.

### Out of scope / boundaries

- Bringing MRD data into CTAM in the first place — that is Epic 1.3 Story 1.3.1, a dependency of this story, not part of it.
- The endpoints already covering other kinds of reference data (regions, offices, calendar, vocabularies, the JOH/jurisdiction/ticket read surfaces) — Epic 1.5, already shipped.
- Any ability to create, edit, or delete MRD-sourced data through this API — never planned, for any phase; corrections happen at the source system and arrive via the next scheduled data sync.

### Recorded deviations

- **The AC's join-key name is itself an open architectural question, not settled by this story.** AC-1 requires "tracing from the judge's identity through to their personnel number" — but a 2026-08-20 reference mock of the real JOH eLinks API found the person record carries **no `personnel_number` field**: "the real API returns `per_id`... and `personal_code`... neither matches the natural-key name CTAM's architecture is built around (`jo_people.personnel_number`, referenced by `ctam_joh_identities`, decision D9...)" [Source: `_bmad-output/planning-artifacts/architecture/gaps.md` → G8.7]. That gap gates on Story 1.1.2 (the tier-(a) schema), not on this story, and `data-tables.md` at `bus_version: arch-v1.1` still names the column `personnel_number` — so this story is correctly written against the currently-published name. If Story 1.1.2 renames the column before this story is dispatched for real, this AC's "personnel number" wording and this story's join must be updated to match; that is a stop (R5) at dispatch time, not something to silently reconcile mid-story. Not approved by anyone — flagged here so the dev agent does not mistake `personnel_number` for a name confirmed against the real upstream feed.
- **Noted, not a defect:** this story only reads whatever rows already exist in `mrd_specialisms` — its own behaviour (success case, empty-list case) does not depend on the shape of the source workbook. But those rows are populated by Story 1.3.1's ETL, which is itself CI-tested only against Epic 0.1's explicitly-provisional, unconfirmed MRD workbook shape [Source: `_bmad-output/planning-artifacts/architecture/gaps.md` → G8.1, 2026-08-21 update]. In any pre-production environment, a thin or oddly-shaped result set from this endpoint may reflect that upstream unknown rather than a defect in this story — worth knowing before treating it as a bug.
