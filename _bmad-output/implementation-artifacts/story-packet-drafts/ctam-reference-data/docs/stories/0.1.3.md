# Story 0.1.3: Deliberately broken practice data proves the validation and rejection logic actually works

Status: ready-for-dev

## Story

As the **engineer building the MRD data-loading work**,
I want the practice workbook to also include realistic mistakes — a missing value, an unresolvable reference, a duplicate drop of the same file — alongside the good data,
so that the checks the data-loading work needs to make are proven to actually catch problems, rather than only ever being exercised against data that's already correct.

## Acceptance Criteria

1. Given the good-case practice workbook from the previous story, when a second version is prepared for validation testing, then it includes at least one row missing a value the data-loading work requires, and at least one row referencing a judge or jurisdiction that doesn't exist anywhere in the practice data, and each broken row is clearly documented as intentional, alongside the specific failure it's meant to trigger.
2. Given the same good-case workbook is provided a second time, when it's used to test re-processing behaviour, then it proves whether processing the same file twice produces duplicate results or correctly recognises it as already handled.

## Tasks / Subtasks

- [ ] Task 1 — Build the deliberately-broken practice workbook variant (AC: 1)
  - [ ] Write the failing test asserting the invalid-variant fixture (once added) contains: at least one row with a required column (per `MrdSpecialismWorkbookSchema`, Story 0.1.1) left blank, and at least one row whose judge reference number or jurisdiction value does not appear anywhere in the good-case fixture (Story 0.1.2) or its cross-referenced JOH practice roster; run it, capture the failure (R2, T1)
  - [ ] Add `src/test/resources/mrd/mrd-specialisms-practice-invalid.xlsx`, derived from the good-case fixture (Story 0.1.2) plus these deliberate faults, keeping every other row good-case-valid so the fixture also proves partial-file rejection is exercised, not just whole-file rejection; re-run, capture the pass
  - [ ] Document each broken row as intentional alongside the specific failure it is meant to trigger — e.g. a companion `src/test/resources/mrd/mrd-specialisms-practice-invalid.md` (or a header/comment row inside the sheet itself, whichever the eventual loader's error reporting can be tested against) naming the row, the fault, and the expected validation outcome named in Epic 1.3's AC ("a row missing a required value", "a row referencing a judge or jurisdiction that doesn't exist")
  - [ ] Write the failing test asserting the documentation artefact names both faults and both expected failures, so the mapping cannot silently drift from the fixture; run it, capture the failure, then add the documentation and re-run
- [ ] Task 2 — Prove the duplicate-drop scenario is representable (AC: 2)
  - [ ] Write the failing test asserting a fixture named as the "second drop" of the good-case workbook (Story 0.1.2's file, provided again) is byte-identical to the original — proving it genuinely represents the same file dropped twice, not a near-duplicate that would mask a real re-processing bug; run it, capture the failure (R2, T1)
  - [ ] Add the second-drop reference (either a literal duplicate checked-in copy or a documented pointer to the same fixture reused twice — prefer reusing the same file by reference over a second checked-in binary, to avoid two copies silently drifting apart, per R14's "no uninvited work" spirit and R6's surface-area discipline); re-run, capture the pass
  - [ ] This story only supplies the practice data the duplicate-drop scenario needs — proving that a *loader* actually avoids creating duplicates is Story 1.3.1's job, not this one's (see Out of scope)

## Dev Notes

### Context distilled from the bus

- `_arch/architecture/gaps.md#g8--upstream-reference-data-integration` (G8.1): the broken rows are deliberate exercises of a provisional, unconfirmed shape — they prove the validation *code path* works against the assumed shape, not that the assumed shape matches what MRD will actually send.
- `_arch/agent-rules/40-data-and-liquibase.md#p5`: "`jo_*` and `mrd_*` are read-only... No `INSERT`, `UPDATE`, `DELETE`, or DDL against upstream-sourced tables from any service other than `ctam-reference-data`'s ingestion path." This story never writes to `mrd_specialisms` itself — it only supplies files a future ingestion path will attempt to write from and correctly reject.
- Epic 1.3's AC (Story 1.3.1) is the actual consumer of this story's fixtures: "the file is validated before anything is written... a workbook fails its validation checks... none of the `mrd_*` tables are changed... the file is instead moved to a `rejected/` path together with a validation report" and "the outcome is exactly the same as the first successful run — no duplicate rows are created" for the re-drop case. This story's fixtures exist to make those Story 1.3.1 behaviours provable; this story does not itself prove them.
- `_arch/agent-rules/50-security-and-logging.md#s16`: the unresolvable judge/jurisdiction reference and the missing-value row must still use synthetic-looking values, not values that could pass for a real personnel number.

### Rules that apply

- R2, T1, T3 (`_arch/agent-rules/00-core.md#r2`, `_arch/agent-rules/10-tdd.md#t1`, `#t3`) — red before green for every fixture-shape assertion; never weaken an assertion to reach green — if a test on the broken fixture needs loosening, the fixture is wrong, not the test.
- R14 (`_arch/agent-rules/00-core.md#r14`) — prefer reusing Story 0.1.2's good-case file by reference for the duplicate-drop scenario over introducing a second checked-in binary; a second copy is exactly the kind of uninvited surface area that can silently drift from the original.
- P5 (`_arch/agent-rules/40-data-and-liquibase.md#p5`) — this story never writes to `mrd_specialisms`; it has no database interaction at all.

### Project Structure Notes

- New fixture: `src/test/resources/mrd/mrd-specialisms-practice-invalid.xlsx`.
- New documentation artefact: `src/test/resources/mrd/mrd-specialisms-practice-invalid.md` (row → intentional fault → expected failure mapping).
- New tests: `src/test/java/uk/gov/hmcts/ctam/referencedata/support/MrdSpecialismsInvalidWorkbookTest.java` and a duplicate-drop assertion (same class or a sibling `MrdSpecialismsDuplicateDropTest.java` — decide by whether the two behaviours share enough setup to belong in one class without breaching M1/M2).
- Depends on Story 0.1.2's `mrd-specialisms-practice.xlsx` (reused, not copied, for the duplicate-drop scenario) and Story 0.1.1's `MrdSpecialismWorkbookSchema` (to know which column is "required" for the missing-value row).

### Out of scope / boundaries

- The good-case workbook itself — covered in Story 0.1.2; this story only adds a second, deliberately-broken variant on top of it.
- Fixing or changing the actual data-loading logic — this work only supplies the practice data it's tested against; Story 1.3.1 (a different, not-yet-built repo state) is where validation and rejection logic, and the actual duplicate-drop idempotency behaviour, get built and proved.
