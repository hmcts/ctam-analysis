# Story 1.1.1: Scaffold `ctam-reference-data` from the HMCTS starter template

Status: ready-for-dev

## Story

As a **platform engineer**,
I want to scaffold the **first** CTAM Pathfinder backend service — `ctam-reference-data` — from HMCTS's standard Spring Boot starter template using the programme's scaffolding script, and deploy it onto the shared cloud environment that already exists,
so that **every service built after it follows the same consistent, secure, version-pinned baseline**, and the team can prove the whole deployment pipeline works end to end against the already-verified shared platform, before any actual business logic is written.

## Acceptance Criteria

1. **Given** the engineer has completed the GitHub manual-setup checklist (empty private `ctam-reference-data` repo created under the HMCTS organisation via the GitHub website; branch protection on `main` requiring PR review, passing status checks, and linear history — no `gh` CLI, per the runbook) and has Java 25, the Gradle wrapper, and Docker installed locally, **when** the engineer runs the programme's scaffolding script against `ctam-reference-data`, **then** it builds a Spring Boot 4.0.x project locally from `hmcts/service-hmcts-crime-springboot-template`, commits with the exact message *"Scaffold CTAM Pathfinder reference-data from HMCTS starter"*, and pushes to the pre-created repo on a feature branch using plain `git` (no `gh`); **and** the Gradle build uses the Groovy DSL with the Spring Boot Gradle plugin 4.1.0 and `io.spring.dependency-management` 1.1.7; group ID `uk.gov.hmcts.ctam`, artefact `ctam-reference-data`, base package `uk.gov.hmcts.ctam.referencedata`, default port 8082; **and** Lombok 1.18.46, MapStruct 1.6.3, JJWT 0.13.0, the OWASP HTML/text encoder 1.4.0, springdoc-openapi, JaCoCo, CycloneDX, the Gradle git-properties plugin, the Gradle versions plugin, and the Gradle Docker Compose plugin are all configured; **and** Spring Boot Test + JUnit 5 (JUnit BOM 6.0.3), Testcontainers for PostgreSQL 1.21.4, Spring Boot's Testcontainers support 4.1.0, and the Spring MVC test starter are set up; **and** Spectral, ArchUnit, Spotless, and Checkstyle are configured; **and** `charts/ctam-reference-data/` (with dev/staging/production overlays), a `terraform/` folder with dev/staging/production stacks for this service's own resources only, CI + deploy-to-{dev,staging,production} GitHub Actions workflows, `CODEOWNERS`, a PR template, and `postman/ctam-reference-data-phase0.postman_collection.json` all exist.
2. **Given** the scaffolded service is running locally (`./gradlew bootRun` against a local Postgres container), **when** the engineer checks `http://localhost:8082`'s health endpoint, **then** it responds `200 OK` with body `{"status":"UP"}`; **and** the info endpoint returns build/git metadata embedded at build time; **and** the readiness endpoint also responds `200 OK`; **and** the service prints structured JSON logs (Logstash Logback Encoder 9.0) to console, with a correlation ID automatically attached to every incoming request — the first place structured logging is exercised in the programme.
3. **Given** the shared cloud environment (Kubernetes cluster, PostgreSQL server, container registry, API gateway, monitoring/logging workspace, secrets store) already built and independently verified in UK South, **when** `ctam-reference-data`'s Helm chart is deployed to the dev cluster, **then** the service successfully reaches the existing shared cluster, database, registry, gateway, and monitoring setup (this story uses that environment; it does not build it); **and** if any part of that shared environment is missing, the deployment fails fast with a clear error rather than failing silently or partway through.
4. **Given** the shared baseline database-migration script (owned centrally, applied before this service's own migrations), **when** it is applied to the dev database, **then** the shared `ctam_configuration_values` table exists and `ctam-reference-data`'s own database role has read (SELECT) access to it; **and** `ctam-reference-data`'s own migration folder exists (with its master changelog file) but is still empty — the actual tables are the next story.
5. **Given** the shared, TLS-verified API gateway, **when** `ctam-reference-data` registers its API through it and a request arrives over HTTP, **then** the service's API is reachable securely over HTTPS, **and** any plain HTTP request is rejected with a redirect to HTTPS.
6. **Given** the shared PostgreSQL server (encrypted at rest, TLS-verified), **when** the dev configuration overlay is applied, **then** the database connection details point at that shared server, which only accepts encrypted connections, **and** `ctam-reference-data` connects successfully using its own dedicated database role.
7. **Given** the shared monitoring workspace (agreed retention policy, already verified), **when** the deployed service sends telemetry, **then** its structured logs and traces land in that workspace.
8. **Given** the engineer pushes the initial commit to a feature branch and opens a PR into `main` through the GitHub website, **when** the CI workflow runs, **then** it runs the build, automated tests, API-contract lint, architecture-rule checks, and code-style/Helm-chart checks; **and** all of those pass on the freshly scaffolded baseline; **and** a test-coverage report is produced.
9. **Given** the PR is merged into `main` through the GitHub website, **when** the deploy-to-dev workflow triggers automatically, **then** the service deploys to the dev Kubernetes cluster in UK South, its container image is pushed to the shared registry, the deployed instance passes its liveness and readiness checks, and the shared monitoring workspace receives its first structured log entries from the service.

## Dev Notes

### Context distilled from the bus

- This is the **first** CTAM Pathfinder service scaffolded, and the first place several bus rules are exercised for the first time in the programme: structured logging + correlation IDs (FR59, `_arch/agent-rules/50-security-and-logging.md#s4`), and the distributed shared-configuration read access (FR8, `_arch/architecture/data-tables.md#shared-infrastructure-tables-no-owning-service--1-table`).
- The HMCTS Crime Spring Boot template (`main`) is deliberately minimal — actuator, observability, logging only. Everything else in AC-1 (Liquibase, Testcontainers, MapStruct, the JWT filter, the OWASP encoder, the Docker Compose plugin, OpenAPI tooling, Helm, Key Vault, the CI quality gates, Pact) is layered on by `ctam-scaffold.sh` from the `hmcts/service-hmcts-springboot-demo` repo plus CTAM's own conventions — it is not in the base template's `build.gradle` [Source: `_arch/architecture/starter-template.md#architectural-decisions-base-template-vs-ctam-scaffolding-overlay`].
- Base-template-verified versions: Java 25, Spring Boot 4.1.x (template `main` pins 4.1.0), Spring Boot Gradle plugin 4.1.0, `io.spring.dependency-management` 1.1.7, `org.cyclonedx.bom` 3.2.4, `com.gorylenko.gradle-git-properties` 4.0.1, `com.github.ben-manes.versions` 0.54.0, `logstash-logback-encoder` 9.0, Lombok 1.18.46, `tomcat-embed-core` 11.0.22 [Source: `_arch/architecture/starter-template.md#a-provided-by-the-base-template-main--verified-in-buildgradle`]. Scaffolding-overlay targets: Testcontainers `spring-boot-testcontainers` 4.1.0 + `testcontainers-postgresql`/`-junit-jupiter` 1.21.4, MapStruct 1.6.3, `jjwt` 0.13.0, `org.owasp.encoder` 1.4.0, `com.avast.gradle.docker-compose` 0.17.21 [Source: `_arch/architecture/starter-template.md#b-added-by-ctam-scaffoldsh--patterns-from-hmctsservice-hmcts-springboot-demo--ctam-conventions-not-in-the-base`].
- Default port 8082 and default group/package (`uk.gov.hmcts.ctam` / `uk.gov.hmcts.ctam.referencedata`) are the scaffolding script's per-service conventions, not the base template's [Source: `_arch/architecture/starter-template.md#per-service-ctam-pathfinder-conventions-encoded-in-scaffolding-script-not-in-shared-library`].
- The shared `ctam_configuration_values` table and its SELECT-only grant are created by `ctam-architecture` in Epic 1.9 Story 1.9.2, applied ahead of this service's own migrations [Source: `_arch/architecture/data-tables.md#shared-infrastructure-tables-no-owning-service--1-table`]. This story only proves this service's role can read it — it does not create the table.
- Every layer of the shared estate this story deploys onto (cluster, database, registry, gateway, monitoring, secrets vault, all UK South) was built and independently checked in Epic 1.0 (Stories 1.0.1–1.0.5) — this story consumes it, per the epic's own framing, and does not build any of it.

### Rules that apply

- `_arch/agent-rules/00-core.md#r2` (red before green, with evidence — applies even to scaffold/infra checks: a file-presence or build-shape assertion counts as the test), `#r6` (no unsanctioned surface area — do not add a dependency, chart value, or workflow step beyond what AC-1 through AC-9 name), `#r7` (never assert a version from memory — read the actual `build.gradle` the scaffold produces rather than trusting the version table above blindly), `#r13` (never write to a protected branch — commit and push on the feature branch only; the PR/merge/deploy steps in AC-8/AC-9 are the human-gated pipeline, not something this session performs).
- `_arch/agent-rules/10-tdd.md#t8` (every schema change gets an `*IT` against real PostgreSQL via Testcontainers — applies to Task 5's baseline-migration proof even though no table is created here).
- `_arch/agent-rules/40-data-and-liquibase.md#p1` (Liquibase, DDL only; the master changelog exists but stays empty this story) and `#p4` (this service may only ever change tables it owns — the shared `ctam_configuration_values` table is read-only here, never touched by this service's own changelog).
- `_arch/agent-rules/50-security-and-logging.md#s4` (correlation ID on every log line, populated by the request-entry filter) and `#s6` (secrets resolve through Azure Key Vault only — the dev database/gateway/monitoring connection details in the config overlays must never be literal secrets in `application-dev.yml`).

### Project Structure Notes

Per `_arch/architecture/conventions.md#structure-patterns`, the scaffold produces:

```
ctam-reference-data/
├── src/main/java/uk/gov/hmcts/ctam/referencedata/
│   └── ReferenceDataApplication.java
├── src/main/resources/
│   ├── application.yml, application-{dev,staging,production}.yml
│   └── db/changelog/db.changelog-master.yaml   (empty this story)
├── charts/ctam-reference-data/                 (dev/staging/production overlays)
├── terraform/{dev,staging,production}/         (this service's own resources only)
├── postman/ctam-reference-data-phase0.postman_collection.json
├── .github/workflows/                          (CI + deploy-to-{dev,staging,production})
├── CODEOWNERS, PR template
├── build.gradle (Groovy DSL), settings.gradle
```

No `controller/`, `service/`, `repository/`, or `domain/` packages beyond the generated `@SpringBootApplication` entrypoint are expected yet — this story adds no business logic (R6). The `terraform/` folder here holds only this service's own secrets-store namespace and (later, in a future story) the weekly MRD file-drop storage; the shared cluster/DB/registry/gateway/monitoring live in `ctam-shared-infrastructure`, not here [Source: epic-1.1's "Hosting" note; `_arch/architecture/repo-structure.md`].

### Out of scope / boundaries

- The 15 outside-sourced `jo_*` tables and the `ctam_sync_status` run-log table — Story 1.1.2.
- The nightly JOH data sync and the weekly MRD data sync themselves.
- CTAM's own reference tables and the read-only reference-data API on top of any of this data.
- All authentication, authorisation, and user-interface work.

### Definition of done

Per `_arch/agent-rules/90-definition-of-done.md`, with these deltas for a pure-scaffold story:

- **Q6** (contract test + Spectral-clean spec per endpoint) — not applicable: this story adds no custom endpoint, only the base template's actuator health/info/readiness. springdoc-openapi is configured and must still generate a valid (if empty) OpenAPI document that passes Spectral, but there is no Pact contract to write yet.
- **Q7** (every schema change proved by an `*IT` from an empty database) — applies narrowly: the empty master changelog plus the shared baseline changelog must both apply cleanly from an empty database; there is no table this story creates.
- **Coverage/mutation floor** (`_arch/agent-rules/10-tdd.md#t16`) — `service`/`domain` packages are empty this story (no business logic yet), so the JaCoCo/PIT gate is expected to pass trivially; it must still run and its output must still be pasted (R12).
- All other Q-items apply as written, including the full `./scripts/verify.sh` gate and the AC → test map.
