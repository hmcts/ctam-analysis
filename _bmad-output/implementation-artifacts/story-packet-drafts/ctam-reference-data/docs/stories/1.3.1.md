# Story 1.3.1: MRD supplementary reference data is ingested from the weekly Excel feed

Status: ready-for-dev

## Story

As the **CTAM Pathfinder platform** (and everyone downstream who relies on judge specialisation data),
I want the MRD team's weekly Excel workbook automatically picked up from its cloud drop-off point and loaded into CTAM's own tables,
so that **supplementary judicial reference data that isn't available from the main judicial data source — most notably judge specialisations — is available inside CTAM without needing to wait for MRD to build its own API**.

## Acceptance Criteria

1. Given a dedicated Azure Storage account and Blob container for the MRD feed have been set up via Terraform in this repo's `terraform/` directory (the first repository in the programme to need this kind of resource), giving the MRD team or operations the ability to drop the weekly workbook, and the Liquibase changeset `db/changelog/002-init-mrd-tables.sql` has created the `mrd_specialisms` table (with further `mrd_*` tables to follow as more of MRD's data comes into scope), owned by `ctam_reference_data` with the same write protection as the existing `jo_*` tables, when the weekly workbook lands in that storage container, then a `@Scheduled` polling task inside `ctam-reference-data` picks it up on its next check.
2. Given the polling task has picked up a workbook, when it processes the file, then the file is validated before anything is written — checking it has the expected sheets and columns, that its values match known reference lists, and that records like specialisations point to real, resolvable JOH personnel numbers and jurisdiction codes — and valid rows are then upserted into the `mrd_*` tables, keyed on the upstream natural key rather than duplicated, and the processed file is moved to an `archive/` path in the container, kept there for audit and traceability, and the run is recorded in the `ctam_sync_status` table, tagged with source `mrd-excel`, together with row counts and outcome.
3. Given the same workbook is dropped a second time, or the task restarts partway through a run, when it processes the file again, then the outcome is exactly the same as the first successful run — no duplicate rows are created, and nothing is updated unnecessarily.
4. Given a workbook fails its validation checks, when the task rejects it, then none of the `mrd_*` tables are changed — the data already in CTAM stays exactly as it was — and the file is instead moved to a `rejected/` path together with a validation report explaining what was wrong, and the failure is recorded in `ctam_sync_status` and written to the platform's structured logs, so the operations team can see it and follow up directly with the MRD team — since corrections always happen at the source, never inside CTAM.
5. Given MRD eventually makes its own API available, when the integration is upgraded to use it, then only the part of the system that fetches the data changes — swapping the file drop-off for a direct API call — while the MRD database tables and everything downstream that relies on them stay exactly as they are.

## Dev Notes

### Context distilled from the bus

- This is a Spring Boot weekly Azure-Blob-drop ingestion story: validate → upsert → archive (or quarantine), idempotent per file, exactly the shape [Source: `_arch/agent-rules/00-core.md`] and [Source: `_arch/agent-rules/40-data-and-liquibase.md`] describe for tier-(a) ingestion.
- **Naming/ownership:** `mrd_specialisms` is a tier-(a), source-prefixed table — "Read-only in CTAM; written only by the ingestion mechanisms" [Source: `_arch/architecture/conventions.md` → "Naming Patterns"]. `ctam_sync_status` is the "Ingestion run log — per-run source, started/finished, outcome, row counts, error detail. CTAM-internal tracking entity with no upstream source" [Source: `_arch/architecture/data-tables.md` line ~78].
- **Write protection:** "The ingestion mechanisms only (`ctam_reference_data` role)" may ever write tier-(a) tables; "Never" from any other role; corrections happen "At source... for `mrd_*`" [Source: `_arch/architecture/data-tables.md` → tier-(a) row].
- **Liquibase is DDL-only** and "never loads upstream data — `jo_*` / `mrd_*` content arrives only through `ctam-reference-data` ingestion" [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P1]. Table ownership is enforced by prefix + `data-tables.md`; only the owning service (`ctam-reference-data`) may create/alter/drop `mrd_*` tables [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P4].
- **Read-only mapping:** "No `INSERT`, `UPDATE`, `DELETE`, or DDL against upstream-sourced tables from any service other than `ctam-reference-data`'s ingestion path. No JPA entity mapped to them is writable — map them read-only" [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P5].
- **Idempotency mechanism:** concurrency and duplicate-avoidance use "a natural-key unique constraint (`uq_{table}_{columns}`)" that "makes a duplicate create fail and maps to 409" — no idempotency-key tables or application-level locking [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P14]. This is the mechanism AC-3's re-processing/restart guarantee must be built on.
- **Schema proof:** every migration (this story's `002-init-mrd-tables.sql`) needs an `*IT.java` run against real PostgreSQL via Testcontainers, asserting the resulting shape and the behaviour that needed it — H2 is prohibited [Source: `_arch/agent-rules/10-tdd.md` → T8] and [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P6].
- **Logging:** never log personnel numbers or PII, even the specialisation-validation failure detail; log the business event and correlation id only [Source: `_arch/agent-rules/50-security-and-logging.md` → S1, S2, S4]. An expected validation rejection is `WARN`, not `ERROR` [Source: `_arch/agent-rules/50-security-and-logging.md` → S3].
- **Time:** if run timestamps or "effective from" style comparisons are needed, use an injected `Clock`, never `now()` directly [Source: `_arch/agent-rules/40-data-and-liquibase.md` → P15] and [Source: `_arch/agent-rules/10-tdd.md` → T12].
- **CI test target:** per the FR-coverage map, this story is "CI-tested against a provisional, explicitly-unconfirmed mock per Epic 0.1" [Source: `_bmad-output/planning-artifacts/epics/fr-coverage-map.md`, NFR24 row] — see "Recorded deviations" below.
