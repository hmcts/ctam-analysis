# Story 0.0.1: Contract endpoints, auth, and pagination are confirmed via the mock

Status: ready-for-dev

## Story

As the **engineer building the nightly JOH data sync** (and everyone who maintains it afterwards),
I want the automated test suite to run against a practice copy that behaves exactly like the real JOH data source — its web addresses, its security checks, and the way it pages through results — rather than a rough stand-in that only covers the easy cases,
so that the sync's routing, security handling, and paging logic are all proven correct before it ever talks to the real system.

## Acceptance Criteria

1. Given the underlying database structure for JOH data already exists, when the engineer builds the practice copy of the JOH data source for automated testing, then it offers the full, confirmed set of lookup, person, and health-check endpoints, reachable both at their standard address and at an alternative address the real system also supports.
2. Every lookup and person endpoint requires a valid security token, clearly rejecting any request with a missing or malformed one.
3. Given the practice copy's "what's changed" and list-style endpoints are queried with valid inputs, when the sync's code asks for everyone updated since a given date, with paging options, then the response matches the confirmed paging format exactly.
4. The results mix full profiles for active people with compact stub records for people who've left or been removed, matching the real system's behaviour.
5. Looking up a single person by their reference always returns their full profile, including past appointments where requested.
6. Looking up someone who has been deleted returns a clear "not found" response.

## Tasks / Subtasks

- [ ] Task 1 — Mount the confirmed endpoint set at both addresses (AC: 1)
  - [ ] Write the failing test asserting `GET /api/v5/healthcheck` (and its alternative-address mount) responds `200`; run it; capture the assertion failure (R2, T1)
  - [ ] Minimum stub-server wiring to pass; re-run; capture the green (T1)
  - [ ] Repeat per endpoint group — root/health, the 11 `reference_data` lookup categories, `people`/`leavers`/`deleted` — one red/green cycle per endpoint, smallest first (T1, T5)
- [ ] Task 2 — Enforce the bearer-token check on every lookup and person endpoint (AC: 2)
  - [ ] Write the failing test for a request with no `Authorization` header expecting the confirmed rejection shape; run; capture red (R2)
  - [ ] Write the failing test for a malformed/garbage token expecting the same rejection shape; run; capture red
  - [ ] Implement the token check once, applied to every lookup/person route (not the two public routes); re-run both tests green
  - [ ] Confirm the public routes (`/`, `/api/v5/healthcheck`) remain reachable with no token (regression test)
- [ ] Task 3 — Reproduce the confirmed pagination envelope on list/change-feed endpoints (AC: 3)
  - [ ] Write the failing test asserting the paging fields/shape on `GET /api/v5/people?updated_since=...&page=...` against the real confirmed envelope; run; capture red
  - [ ] Minimum implementation to pass; re-run
  - [ ] Repeat for `/leavers` and `/deleted`, each keyed on its own required from-date parameter
  - [ ] Failing-then-passing test for the "required from-date is missing" case being rejected before pagination logic runs
- [ ] Task 4 — Mixed full-profile / stub-record change-feed results (AC: 4)
  - [ ] Write the failing test: a change-feed page containing an active person (full profile) and a left/removed person (compact stub) in the same response; run; capture red
  - [ ] Minimum fixture/serialisation logic to pass; re-run
- [ ] Task 5 — Single-person lookup, including past appointments (AC: 5)
  - [ ] Write the failing test for `GET /api/v5/people/:id` returning the full profile; run; capture red
  - [ ] Write the failing test for `?include_previous_appointments=true` including past appointments in the response; run; capture red
  - [ ] Minimum implementation for both; re-run
- [ ] Task 6 — Deleted-person lookup returns "not found" (AC: 6)
  - [ ] Write the failing test: `GET /api/v5/people/:id` for an id present only in the deleted feed returns the confirmed not-found shape; run; capture red
  - [ ] Minimum implementation to pass; re-run

## Dev Notes

### Context distilled from the bus

- This story mocks a **third-party** contract (the real JOH eLinks API). The bus pins CTAM's *own* API conventions (`_arch/architecture/conventions.md`), not eLinks's — do not reach for CTAM's cursor/offset pagination envelope, RFC 9457 error shape, or `/v1` versioning rules when shaping the mock's responses (those govern what `ctam-reference-data` itself publishes, not what this fixture reproduces). The mock's actual field/envelope shapes come from the real Swagger export and example payloads this story was scoped against — source materials that are **not** part of `_arch` and must be supplied alongside this packet when it is really dispatched (R4 — if they are missing, that is a stop, R5).
- [Source: `_arch/architecture/gaps.md#g8-1`] — at this packet's pinned `bus_version` (`arch-v1.1`), gap G8.1 still reads the eLinks contract as **unconfirmed**, assuming `jo_people` keys on `personnel_number`. This story (plus 0.0.2) is what confirms most of that structural uncertainty in practice; the assumption about the natural-key field name specifically is not resolved here (that is Story 0.0.3) and must not be treated as settled by anything built in this story.
- [Source: `_arch/architecture/data-tables.md#tier-a--joh-elinks-upstream-sourced--15-tables`] — the 15 `jo_*` entities this mock's lookup/person endpoints must cover, and their consuming services, so the endpoint inventory in the epic (11 `reference_data` categories + `people`/`leavers`/`deleted`) can be checked against what `ctam-reference-data`'s schema actually expects to ingest.
- [Source: `_arch/architecture/repo-structure.md#complete-project-directory-structure--per-backend-service`] — confirms `src/test/java/uk/gov/hmcts/ctam/referencedata/` already has `controller/`, `service/`, `repository/`, `client/` subpackages; there is no existing convention for a third-party mock/fixture harness (see *Project Structure Notes* below).

### Rules that apply

- [`_arch/agent-rules/00-core.md#r1`] Scope is exactly the six ACs above — do not build endpoints or behaviour the epic did not list (e.g. do not add error-shape fidelity or realistic seed volumes; that is 0.0.2).
- [`_arch/agent-rules/00-core.md#r5`] If any endpoint's exact response field names, the pagination envelope's exact field names, or the bearer-token rejection body cannot be pinned to the real Swagger export / example payloads, stop and record the question rather than inventing a shape.
- [`_arch/agent-rules/10-tdd.md#t1`], [`#t2`] Red-first per behaviour; a compile error is not red — introduce the minimum signature first.
- [`_arch/agent-rules/10-tdd.md#t7`] This is exactly the kind of behaviour T7 rations `@SpringBootTest` for if the mock is wired as an in-process Spring component (a filter chain / scheduled trigger) — prefer a sliced test per endpoint group over one full-context test per behaviour.
- [`_arch/agent-rules/10-tdd.md#t9`] The nightly sync will be a **consumer** of this contract; building this mock is this story's half of that consumer-contract-testing discipline (T9's "consumer test for what you call") even though there is no Pact broker involved — it is a hand-built stand-in for the same purpose.
- [`_arch/agent-rules/10-tdd.md#t12`] No wall clock, no real network, no randomness in the mock's own tests — the mock is exercised in-process or via a local Testcontainers-style harness, never against anything reachable over the network.
- [`_arch/agent-rules/50-security-and-logging.md#s7`] Any bearer token used in these tests must be self-evidently synthetic — never a real eLinks credential, never a plausible-looking one.
- [`_arch/agent-rules/50-security-and-logging.md#s16`] Fixture/person records used to prove pagination and profile-shape behaviour must be synthetic, never real judicial data, even at this small scale (0.0.2 raises the volume; this story sets the pattern).

### Project Structure Notes

- No existing `_arch` convention names a location for a third-party API mock. Per [`_arch/agent-rules/10-tdd.md#t14`] ("test data builders live in `src/test/java/.../support/`"), the most consistent placement is a dedicated support package: `src/test/java/uk/gov/hmcts/ctam/referencedata/support/elinks/` for the mock-server harness and fixture builders, with stub-mapping/response-payload resources (if the mock is WireMock-backed) under `src/test/resources/elinks-mock/`. Record the actual choice here once made — this is a decision the epic leaves to the implementing team, not something `_arch` currently specifies (R6 is satisfied by the story itself sanctioning a mock/fixture layer; the *location* still needs a stated reason in the handoff).
- Both the standard and alternative addresses for each endpoint should be expressed as two route mappings onto the same handler, not duplicated logic, to keep Task 1 from doubling the size of every later task.
