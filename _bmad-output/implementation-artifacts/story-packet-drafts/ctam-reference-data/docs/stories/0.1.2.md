# Story 0.1.2: A realistic sample workbook is built for CI at a believable scale

Status: ready-for-dev

## Story

As the **engineer building the MRD data-loading work**,
I want a practice copy of a workbook in the proposed shape, populated at a believable scale rather than a handful of hand-picked rows,
so that the data-loading work's behaviour can be checked against something that resembles the real thing, not an unrealistically small or convenient test case.

## Acceptance Criteria

1. Given the proposed workbook shape from the previous story, when the engineer builds the practice workbook for automated testing, then it contains enough rows to be a believable stand-in for a real weekly drop — spanning multiple judges, multiple jurisdictions, and multiple specialism codes — not just two or three examples, and every reference in the practice data (a judge, a jurisdiction) resolves cleanly against the practice data used elsewhere in automated testing, so the good-case rows are internally consistent.
2. Given the practice workbook is used in automated testing, when it's read by the data-loading logic, then it behaves as a normal, well-formed input file would.

  - [ ] If none exists yet, this is a stop (R5): record it in *Open Questions* rather than adding a new dependency unsanctioned (R6) — the library choice affects Story 1.3.1's production loader too, and picking it silently here would pre-empt that story's own decision.

## Dev Notes

### Context distilled from the bus

- `_arch/architecture/gaps.md#g8--upstream-reference-data-integration` (G8.1, 2026-08-21 update): this fixture is built against Story 0.1.1's provisional, explicitly-unconfirmed shape — it must not be presented as validated against a real MRD example, because none exists.
- `_arch/architecture/conventions.md#naming-patterns`: `mrd_specialisms` is tier-(a), read-only in CTAM, written only by the ingestion mechanism (Story 1.3.1). This fixture is consumed by that ingestion path in tests; it is never loaded via Liquibase (`_arch/agent-rules/40-data-and-liquibase.md#p1`: "Liquibase... never loads upstream data — `jo_*` / `mrd_*` content arrives only through `ctam-reference-data` ingestion").
- `_arch/agent-rules/50-security-and-logging.md#s16`: "Test fixtures... all use synthetic data." Every judge reference number, jurisdiction, and specialism value in this fixture must be synthetic, matching the synthetic roster used by the sibling Epic 0.0 mock, never a real personnel number or a value that resembles one.

### Rules that apply

- R7 (`_arch/agent-rules/00-core.md#r7`) — never assert the spreadsheet library from memory; read `build.gradle`.
- R6 (`_arch/agent-rules/00-core.md#r6`) — a new dependency (if the library isn't already present) is unsanctioned surface area unless the story or a cited convention calls for it; this is why Task 0 is a blocking stop-and-ask, not an assumption.
- T10, T12 (`_arch/agent-rules/10-tdd.md#t10`, `#t12`) — no network in the test; reading the checked-in classpath fixture is a deterministic, local read, not a flaky external dependency.
- S16 (`_arch/agent-rules/50-security-and-logging.md#s16`) — synthetic data only, ever.

### Project Structure Notes

- New fixture: `src/test/resources/mrd/mrd-specialisms-practice.xlsx`.
- New test: `src/test/java/uk/gov/hmcts/ctam/referencedata/support/MrdSpecialismsPracticeWorkbookTest.java` — reads the classpath fixture directly; no Spring context, no database, so this stays a plain unit-style test per T7 rather than an `*IT.java` — reading a static, checked-in classpath resource is not the kind of filesystem/network nondeterminism T10/T12 guard against, but flag this taxonomy call if a reviewer disagrees (R5).
- Depends on `MrdSpecialismWorkbookSchema` from Story 0.1.1 (`src/test/java/uk/gov/hmcts/ctam/referencedata/support/`) to assert the fixture's shape against a single source of truth rather than a second, drifting copy of the column list.
