# Epic 0.6: MRD reference data is served read-only via a versioned, jurisdiction-filtered API

**User outcome:** MRD-sourced supplementary judicial reference data — notably JOH Specialisations, ingested in **Epic 0.3** — is queryable read-only via `ctam-reference-data`'s versioned REST API, **jurisdiction-filtered**[^d8], on its own API surface separate from the JOH + tier-(b) read API (**Epic 0.5**). MRD is a distinct upstream source with its own ownership boundary, cadence, and contract; giving it a dedicated read API keeps that boundary visible at the API layer, not just in the ingestion mechanism. **No admin UI is in scope for MVP**; MRD data is never hand-edited in CTAM (corrections at source per FR6).

**Depends on Epic 0.1** (schema design), **Epic 0.3** (MRD tier-(a) data), and **Epic 0.4** (auth — read endpoints are downstream of `JWTFilter` + `authz/check`, per D8).

**Vertical slice:**
- Reference Data **read-only** REST API over MRD tier-(a) data (`mrd_specialisms`, and further `mrd_*` tables as MRD entities enter scope per Epic 0.3), **jurisdiction-filtered responses**[^d8], for consumption by `ctam-ui`, downstream services, and OpenAPI clients. **No `POST`/`PUT`/`DELETE` endpoints** — MRD tier-(a) tables are written only by the Epic 0.3 ingestion mechanism
- Same API-as-Product read-side standards as Epic 0.5: URL versioning (`/v1/reference-data/...`), OpenAPI 3.x spec published (by Gradle `maven-publish`) as a Maven-format artefact, RFC 9457 problem-details errors, RFC 9745 `Deprecation` + RFC 8594 `Sunset` deprecation signalling (FR58)
- Extends the Phase 0 Postman collection (`postman/ctam-reference-data-phase0.postman_collection.json`, first published in Epic 0.5) with MRD read coverage

**FRs covered:** FR6 (read API over MRD tier-(a) data), FR7 (direct-SQL read pattern), FR58 (versioned read API contract), FR59 (structured logs)

**Key NFRs:** NFR14 (no forbidden data), NFR40 (service independently deployable), NFR42 (Postman collection). **NFR17–NFR19 (accessibility) do not apply in Phase 0** — no UI surface for this domain is delivered.

**Out of scope for Phase 0 (deferred post-MVP):**
- Admin-gated write endpoints on the MRD read API (MRD tier-(a) never gets a CTAM write surface, in any phase)
- `ctam-admin-ui` MRD maintenance module
- JOH + tier-(b) read endpoints — Epic 0.5
- MRD API integration (post-MVP — when MRD ships public APIs; the reader component behind Epic 0.3's ingestion swaps, this read API is unaffected)

## Story 0.6.1: MRD reference data read-only REST API with jurisdiction filtering, versioning, OpenAPI, RFC 9457 errors

As an **API consumer** (`ctam-ui` now; downstream services in Phase 1+, notably `ctam-joh` composing JOH profiles with Specialisations),
I want a versioned **read-only** REST API over MRD-sourced reference data with **jurisdiction-filtered responses**, full OpenAPI spec, RFC 9457 error envelopes, and APIM-injected deprecation headers,
So that **Phase 1+ services can query MRD Specialisations at runtime, scoped to the requester's jurisdiction**[^d8], on an API surface that reflects MRD's distinct upstream ownership boundary rather than being blended into the JOH + tier-(b) API.

**Acceptance Criteria:**

**Given** `ctam-reference-data` carries MRD tier-(a) data per Epic 0.3, Story 0.3.1,
**When** the engineer implements read endpoints,
**Then** `GET /v1/reference-data/mrd/specialisms` (and further `GET /v1/reference-data/mrd/{entity}` endpoints as MRD entities enter scope) returns `200 OK` with structured JSON,
**And** read endpoints are protected by `JWTFilter` (any authenticated principal can read; per NFR13),
**And** **responses are filtered by the requester's jurisdiction** resolved from `AuthDetails` (D8/FR2) — a Specialisation entry is scoped to the JOH personnel numbers and jurisdiction it applies to,
**And** the API documents that it serves MRD tier-(a) data only — it does not blend with the JOH/tier-(b) resources in Epic 0.5 (FR6),
**And** **no write endpoints** (`POST`, `PUT`, `PATCH`, `DELETE`) are implemented — controller layer rejects with `405 Method Not Allowed` and an RFC 9457 problem-details body explaining that MRD corrections happen at source,
**And** OpenAPI spec generated by springdoc lists the MRD read endpoints with full request/response schemas, as an addition to the existing `api-ctam-reference-data` spec (same artefact, same service — Epic 0.5 and Epic 0.6 are one deployable with two API surfaces).

**Given** the engineer implements pagination + filtering,
**When** a consumer queries `GET /v1/reference-data/mrd/specialisms?personnelNumber=12345&page=1&size=50`,
**Then** the response includes paginated data with the same standard envelope used in Epic 0.5 (`{items, page, size, totalElements, totalPages}`),
**And** invalid query parameters return `400 Bad Request` with RFC 9457 problem-details (per AR37, NFR39).

**Given** the OpenAPI spec is regenerated and Spectral lint runs in CI,
**When** the spec is built,
**Then** the spec passes Spectral lint (per AR17),
**And** the republished `uk.gov.hmcts.ctam:api-ctam-reference-data` artefact (per AR8) includes the MRD endpoints alongside the Epic 0.5 endpoints,
**And** Swagger UI is exposed for developer browsing (ops-restricted at APIM), showing both API surfaces.

**Given** APIM is configured for `ctam-reference-data` per AR27 + AR39 (established in Epic 0.5),
**When** a response to an MRD read endpoint leaves APIM to the client,
**Then** rate-limit headers are present per APIM policy,
**And** `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) headers are injected on any MRD endpoint flagged in the OpenAPI spec as `deprecated: true` (none at Phase 0),
**And** `/actuator/*` paths remain blocked at APIM (per AR33) — unaffected by this addition.

**Given** the engineer extends the Phase 0 Postman collection,
**When** the collection runs in CI,
**Then** `postman/ctam-reference-data-phase0.postman_collection.json` exercises every MRD read endpoint,
**And** the collection covers happy path + jurisdiction filtering + 400 (invalid query) + 401 (unauthenticated) + 405 (write attempt) (per NFR42),
**And** the collection is versioned alongside the service (same collection file as Epic 0.5 — one service, two documented API surfaces).

**References:** FR6 (read surface over MRD tier (a)), FR7, FR58, FR59; NFR12, NFR13, NFR14, NFR39, NFR42; AR8, AR17, AR27, AR33, AR34, AR37, AR38, AR39, AR41; D8.

**Explicitly NOT in scope (deferred post-MVP):**
- Admin write endpoints for MRD data (never, in any phase)
- JOH + tier-(b) read endpoints — Epic 0.5
- MRD API integration (post-MVP — reader-component upgrade behind Epic 0.3's ingestion; this read API is unaffected by that upgrade)

[^d8]: D8 — rollout is jurisdiction-first, then per-region; jurisdiction is a first-class hierarchical attribute.
