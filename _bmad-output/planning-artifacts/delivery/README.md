# Delivery Control Plane

This folder is the **control plane** for CTAM Pathfinder delivery. It lives in `ctam-analysis` and orchestrates *what to build next*, *whether it traces to a requirement*, and *how a finished story reports back* — **without ever editing service code**. Full rationale: [`../architecture/delivery-operating-model.md`](../architecture/delivery-operating-model.md).

> **Rewritten 2026-08-19 (SCP 2026-08-19d).** Two bespoke artefacts were retired in favour of BMad's own: the per-epic **traceability ledger** and **`dispatch-graph.yaml`**. Delivery state now lives where BMad puts it, and the structured facts BMad does not model live in the epic and story files themselves. This folder is what remains.

## Where delivery state lives now

| Fact | Home | Notes |
|---|---|---|
| Story and epic **status** | `_bmad-output/implementation-artifacts/sprint-status.yaml` | Generated by `bmad-sprint-planning`; read by `bmad-create-story`, `bmad-dev-story`, `bmad-sprint-status`. **One** status vocabulary: `backlog → ready-for-dev → in-progress → review → done` |
| Which **repo** an epic lands in | the epic's frontmatter (`repo:`) | May be a list — Epic 1.4 spans three repos |
| Build **order** | the epic's frontmatter (`depends_on:`) | Phases 0 and 1 are structured; phases 2–8 are prose in [`../epics/framework.md`](../epics/framework.md) → *Phase dependency order* until they are decomposed |
| A story's **requirements, target repo and bus version** | the story packet's frontmatter, in the service repo | `frs`, `nfrs`, `repo`, `bus_version`, `sprint_status_key` |
| **Who** is working on a story | the branch on the target remote, and the PR | No `owner` field anywhere — a branch *is* the claim |
| **PR** link | the PR itself, and the packet's Dev Agent Record | |

Not here, deliberately: the **context bus** (`ctam-architecture` publish + `arch-vN` tag) and **per-repo scaffolding** — those are [Epic 1.9](../epics/phase-1/epic-1.9-context-bus-and-shared-baseline.md) and downstream work. The control plane only ever *references* a `bus_version` as a string.

## The delivery loop

```
[ctam-analysis: control plane]                    [ctam-{service}: execution unit]
  1. SELECT next  ── sprint-status.yaml (what is backlog) + the epic's depends_on
        │           ./scripts/dispatch-preflight.sh <story-id>
        │
  2. DISPATCH ──── bmad-create-story → story packet (story + Gherkin ACs +
        │          distilled context + pinned bus_version)
        │          in the target repo: git switch -c story/<id>
        │                              land docs/stories/<id>.md, commit, push
        │          sprint-status.yaml: backlog → ready-for-dev
        │          ── the pushed branch IS the claim on this story ──
        │                                                 ▼
        │                                    3. EXECUTE bmad-dev-story in the repo
        │                                       ON THE SAME branch story/<id>
        │                                       (reads CLAUDE.md → _arch/ bus)
        │                                       packet Status: in-progress → review
        │                                       commits → push → human opens the PR
        │                                                 │  (human reviews + merges)
  4. SIGNAL ◄──────────────────────────────────────────────┘
        └ sprint-status.yaml: → done   (bmad-sprint-status)
```

**Buildable-now rule:** an epic is dispatchable iff every epic in its `depends_on` is `done` in `sprint-status.yaml`. Epics with disjoint dependency sets and no shared state may run **in parallel** — Epic 1.8 (Notification) needs only the estate, so it can run alongside 1.1/1.2/1.3/1.4.

## BMad skill mapping

| Step | Skill | Runs in |
|---|---|---|
| Plan | `bmad-sprint-planning` (parses the epics → `sprint-status.yaml`) | `ctam-analysis` |
| Select | `scripts/dispatch-preflight.sh` (read-only pre-flight) | `ctam-analysis` |
| Dispatch | `bmad-create-story` → story packet in the target repo | `ctam-analysis` |
| Execute | `bmad-dev-story` → `bmad-code-review` | target repo |
| Signal | `bmad-sprint-status` | `ctam-analysis` |

`bmad-create-story` refuses to run without `sprint-status.yaml`, so **sprint planning comes first**, once per phase. Team overrides that adapt the BMad skills to this polyrepo live in `_bmad/custom/` (committed).

## Multi-user coordination

**One dispatcher at a time, by convention.** `sprint-status.yaml` is a single file, so two people dispatching concurrently would conflict on it. Coordinate before you dispatch.

The backstop is [`../../../scripts/dispatch-preflight.sh`](../../../scripts/dispatch-preflight.sh), which is read-only and answers three questions:

1. Is the story still `backlog` in `sprint-status.yaml`?
2. Does a branch on the target remote already name it? — **a branch is the claim**; there is no `owner` field to contend over
3. Are the epic's `depends_on` all `done`?

**Dispatch creates that branch.** `story/{story-id}` is cut in the target repo at dispatch, the packet is committed on it and pushed, and the implementing session continues on the **same** branch — one branch per story, from dispatch to PR (`conventions.md` → *Git conventions*, amended 2026-08-20). Pushing matters: the pre-flight check reads the remote, so an unpushed branch claims nothing.

Execution parallelises freely: work happens in different service repos, where branches and PRs already show who is doing what.

## Conventions

- **One status vocabulary**, BMad's: `backlog → ready-for-dev → in-progress → review → done` (epics: `backlog → in-progress → done`). A story packet carries the same vocabulary in its `Status:` line and nowhere else.
- **FR granularity:** epic-level unless a story narrows it. Every FR/NFR should trace to at least one story once all phases are decomposed. The reverse lookup ("which stories cover FR6?") is a **generated** report over packet frontmatter, not a maintained table.
- **One branch per story**, `story/{story-id}`, created at dispatch and carried through to the PR. **`main` is protected; the PR is the human gate** — an agent branches, commits and pushes; a human opens, reviews and merges.
- **Bus pinning:** a story records the `bus_version` it was built against; repos re-sync only via an explicit submodule bump.
